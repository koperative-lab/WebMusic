# 0.3.0 modular release preparation and migration

This checkout prepares a shared `0.3.0` release of Kernel, UI Kit, Score, Audio
and Bridge. It is not a publication receipt. Follow [Publishing](PUBLISHING.md)
for the manual release procedure and [STATUS](../STATUS.md) for current gates.

## Registry baseline and dependency floor

A public registry query on 2026-10-15 (America/New_York) confirmed that all five
`0.2.0` artifacts already exist and are tagged `latest`; the remote `v0.2.0` tag
also exists. Their bytes must not be overwritten and that tag must not move.
The query found no `0.3.0` artifact. Repeat registry and tag checks immediately
before publication: a preparation-time query does not reserve a version.

All five package versions are now `0.3.0`, and internal dependency/peer ranges
are `^0.3.0`, including the private documentation workspace. The lockfile
changes only those six workspace records; this preparation does not upgrade
third-party dependencies. Node support remains entry-specific and unchanged.

The dependency floor is required, not cosmetic. Published Kernel `0.2.0` lacks
`@webmusic/kernel/module` and `@webmusic/kernel/session`; published UI `0.2.0`
lacks `@webmusic/ui/patch-editor`. New Score/Audio implementations import the new
Kernel entries. Merely changing their version while retaining `^0.2.0` peers
would permit a successful install that fails at import time. Upgrade the WebMusic
packages used by an application together, and keep third-party integrations on
their documented optional entries.

## Adopting modular composition

The [runnable composition guide](../../apps/doc/webmusic/src/content/docs/bridge/modular-composition.mdx)
owns executable examples. These are the principal adoption choices:

- Modular composition is the only model (DEC-068); there is no opt-in
  attribute. The outermost player owns the Session and nested players join it;
  an outermost Rack or mixer owns the Session of its members; a standalone
  player is a Session of one. Use `session="local"` for an independent
  transport boundary. Companions connect by containment or `input="#id"`.
- Use stable audio ports and connection leases for replacement, sends and taps.
  Sharing an AudioContext does not imply sharing transport time. Score/Audio
  mappings must name their axes, offsets and positive scales; Bridge owns
  semantic cross-domain conversion.
- Effects share `InsertChain`; replacing an insert preserves the player and
  position. `.effect` remains a one-slot compatibility shorthand. Crossfades
  and tails have explicit ownership and bounded retirement.
- A `score-synth-panel` attached by target or module scope edits borrowed
  parameters and owns no DSP. `mode="insert"` explicitly selects its standalone
  insert contract. Removing attached UI does not destroy its instrument or LFO.
- Modular `score-note-input` automatically borrows the nearest supported
  instrument. Existing callbacks still receive events; use `routing="manual"`
  if a callback already plays the synth, to avoid duplicate notes. Occurrence IDs
  keep overlapping same-pitch notes independent.
- Parameters, native CV/LFO, macros, per-voice ADSR and Session-relative
  automation share the same parameter handles. A manual base write takes over
  a parameter from its automation. Real-time clock advancement is reconciled
  when submitting a trajectory; it is not a reason to abandon a valid track.

See the owning [Score player](../../apps/doc/webmusic/src/content/docs/score/element/play/score-player.mdx),
[synth panel](../../apps/doc/webmusic/src/content/docs/score/element/play/score-synth-panel.mdx),
[Audio mixer](../../apps/doc/webmusic/src/content/docs/audio/headless/play/audio-mixer.mdx)
and [Kernel](../../apps/doc/webmusic/src/content/docs/kernel/api.mdx) references
for exact members, modes, failure behavior and teardown.

## Breaking changes from 0.2 (DEC-068, MOD-15)

`0.3.0` is unpublished, so the single composition model replaces the 0.2
surfaces below without a deprecation period. The architecture check rejects
their return (MC-27).

| Removed | Replacement |
| --- | --- |
| `composition="modules"` attribute and Kernel `isModularComposition()` | Nothing to set: every Element composes through modules; an undefined custom element is a pending boundary only inside a provider's scope |
| `player="#id"` on Score and Audio views, analysis, meter, recorder, playlist and mixer; `source="#id"` on `score-pitch-view` and `audio-live-view` | `input="#id"`, or nest the element inside the player, Rack part or mixer. The object properties (`.player`, `.inputModule`, `.analyser`, `.context`) remain |
| Audio analysers and the meter borrowing a linked player element's `.analyser` | A side tap on the linked module's audio port; the linked module's transport resets readings and its loading or error state appears in the status |
| `@webmusic/kernel/sync` entry, `TransportGroup` as public API, `MirrorClockMaster` | `@webmusic/kernel/session`: `SessionTransport.register()` with a `ParticipantTiming`; the participant and command types are exported from `/session` |
| Bridge `ScoreAudioSync`, `createSyncedPlayback`, `createAudioMasteredPlayback`, `clipAsMaster`, `scoreAsFollower`, `transport-contracts` | `createScoreAudioSession(score, clip, options)` and `registerAudioParticipant(session, player, options)` |
| Score `LoopPlayer`, `AbPlayer`, `TonePlayer`, `bindClock`, `Player` and `MidiPlayerController` aliases | A `score-player` or `ScorePlayerModule` in a Session; Session loop and range; `ScorePlayer` and `PlayerController` |
| Score `score-rack-control` relying on an enclosing player for transport | An outermost desk owns its Session; read it from `.sessionTransport` |

New module surfaces: the five Kernel port families with `ModuleHandle.ports()`
and `getModulePort`, `RackModule`, `createProviderScope`, `DeviceSink`,
`CaptureSink`, `createOfflineModuleEnvironment`, `checkModuleConformance`;
`AudioPlayer.module` and `AudioMixer.module` enumerate their ports; Score React
`useSessionSnapshot` and `useModulePorts`. Later rounds add Kernel
`observeCompanionInput`, `renderModuleGraph`, `isOfflineModuleContext`,
`SessionParticipantLease.refresh()` and an environment `createTickSource`;
`.inputModule` and `port` on every Score view and analysis Element;
`score-note-input.module` (a `notes` output) and `score-recorder` `input`,
`port`, `.inputModule` and `.module` (a `notes` input, plus an `output` bus
inside a provider); `AudioPlaylist.outputPort`,
`peekOutputPort()`, `onTrackChange()`, `preload()` and `adoptAudioContext()`; `AudioMixer` `channel:<id>` ports and
`channelOutput(id)`; `ScorePlayer.replaceScore()` / `replaceSynth()` and their
`ScorePlayerModule` counterparts.

Behavior changes without a removed name: a playlist's entries play through one
queue bus before its destination; a player over a borrowed queue registers it
once with the Session on `queue-entry-seconds` instead of once per entry; and
assigning `.score` or `.sound` to a mounted `score-player` keeps its engine
instead of rebuilding it; inside a desk a `score-recorder`'s live monitoring and
auditions play on one channel named by the recorder's ID instead of one new
channel per audition (monitoring previously bypassed the desk); and Bridge
`registerAudioParticipant` no longer asks an engine without shared Session
scheduling (an editor document, a media stream) to activate, so such players
start instead of rejecting.

## Project files and editing

Kernel supplies versioned, bounded project data and transactional runtime
restoration. Bridge registers domain-specific factories. The application owns
asset resolution, persistence, undo and plugin availability; unresolved modules
retain their data for later recovery. Restore defaults to paused. Audio device
latency, background scheduler stalls and arbitrary plugin behavior are not
automatically compensated.

The UI [patch editor](../../apps/doc/webmusic/src/content/docs/uikit/parameters-gestures/patch-editor.mdx)
uses structural bindings and supplies keyboard-equivalent audio/CV editing.
Default routes remain explained and read-only. A committed graph edit and a
subsequent presentation refresh failure are distinct outcomes; the UI must remain
usable after the latter. Serialization rejects encoded output exceeding the
parser's text budget before returning it, rather than producing an unreadable
save file.

## Release validation and delivery

The [repair record](../audits/2026-10-15/MODULAR-RELEASE-FIXES.md) retains local
checks, native/browser results, registry evidence and artifact fingerprints.
The [twelve-finding follow-up](../audits/2026-10-16/MODULAR-RELEASE-FOLLOWUP-FIXES.md)
records subsequent ownership, clock, CommonJS composition and editor repairs.
The [hardening record](../audits/2026-10-16/MODULAR-RELEASE-HARDENING.md)
adds initial-attachment/mixer reentry repairs, a scoped development dependency
fix and verified original demo media, including normal and Pages browser checks.
Historical `0.1.0` Agent Toolkit receipts and the earlier
[0.2.0 migration guide](0.2.0.md) remain unchanged; neither substitutes for this
candidate's release validation.

From a clean reviewed release commit, run the complete check, documentation
build, production audit and external-install check in [Publishing](PUBLISHING.md).
Verify that exact commit's Node 22.22.3/24 quality jobs and Pages build. Inspect
all five tarballs, repeat the real-time automation and borrowed-group mute
acceptance, and confirm that old foundation versions are rejected by the new
peer floor. Exercise Audio loader-to-Bridge asset admission and UI root/subpath
presenter identity in both runtime formats from the installed tarballs. If the
publishing SHA or artifacts change, repeat affected checks.

Publish in Kernel, UI, Score/Audio, Bridge dependency order, verifying each exact
version before proceeding. After a fresh registry installation succeeds, tag
the producing commit as described by Publishing and create a new verified
release receipt from actual registry metadata. Local preparation, a Git tag or
a successful build does not establish registry delivery.

Website deployment is separate. The formerly unresolved resources were replaced
by original MIT-licensed study media or removed when unused. The
[asset inventory](../../apps/doc/webmusic/ASSETS.md) records the generating source,
notices and exact hashes; `check:demo-assets` runs in both site build commands.
Those site files are excluded from npm tarballs. Review the final Pages build
before selecting `deploy_pages`; the replacement does not change an older
deployment or assign rights to the removed recordings and SoundFonts.
