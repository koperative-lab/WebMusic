# 0.2.0 release preparation and migration

This guide prepares the first shared release of Kernel, UI Kit, Score, Audio
and Bridge. It does not assert that `0.2.0` is published. Use the current
[STATUS](../STATUS.md) for unresolved work and recorded validation; follow
[Publishing](PUBLISHING.md) for the release procedure and
[Releasing](RELEASING.md) for version policy.

## Release scope and dependency compatibility

All five packages target `0.2.0`. Audio and Bridge start at `0.2.0` so their
first registry artifacts use the same version as their required foundations.
Score and Audio require Kernel `^0.2.0`; their visual entries also need the
optional UI peer `^0.2.0`. Bridge requires Kernel, Score and Audio `^0.2.0`.
UI has no dependency on the other four packages. In these ranges, `^0.2.0`
accepts `0.2.x`, so upgrade the packages used by an application together.

Current Audio uses `AnalyserMeter.configure()` and four UI analyzer entries
that are absent from the published `0.1.0` foundations. Bridge also relies on
the updated transport lifecycle behavior. Publishing Audio/Bridge against
the old `^0.1.0` peer ranges would therefore misstate compatibility.

Audio supplies clips, decoding, playback/capture, analysis/transcription,
views and browser/React adapters. Bridge supplies Score/Audio synchronization,
offline score rendering, transcription assembly and timeline conversions.
Read the [Audio README](../../packages/audio/README.md) and
[Bridge README](../../bridges/score-audio/README.md) for optional integrations,
resource ownership and environment requirements. Audio/Bridge declare Node
`^22.22.3 || ^24.16.0 || >=26.3.0`; Kernel/UI/Score retain `>=22`.

### Score Analyze Elements

The published `0.1.0` Analyze Element entry exported five tools. `0.2.0`
retains `ChordAnalysisElement` and `LiveChordAnalysisElement`. It removes
`KeyAnalysisElement`, `RomanAnalysisElement`, `VoiceLeadingAnalysisElement`
and their three `define*Element` functions. `defineAllAnalysisElements()` now
registers only the two retained, domain-prefixed tags.

Applications needing key, Roman-numeral or voice-leading reports should use
`detectKey`, `romanNumerals` or `voiceLeading` from `@webmusic/score/analyze`
and compose their own presentation. There is no direct replacement Element
for those three removed tools. Motif and rhythm algorithms also remain in
API/Headless; the parked recurrence Elements were development work, not part
of the compared `0.1.0` npm Element surface.

The retained chord lane adds local selection and inspection. The live-chord
tool follows player note events; its supported attributes focus on `player`,
`density`, `scheme`, `spelling`, `alternates` and `stability-ms`. Migrate old
live-chord uses of score-source/timeline attributes to the chord lane or a
Headless/API composition. Review the current
[chord lane](../../apps/doc/webmusic/src/content/docs/score/element/analyze/score-chord-analysis.mdx),
[live-chord tool](../../apps/doc/webmusic/src/content/docs/score/element/analyze/score-live-chord-analysis.mdx)
and [Analyze API](../../apps/doc/webmusic/src/content/docs/score/api/analyze.mdx)
before updating event handlers and custom styling.

### Kernel and UI

Kernel retains its public subpaths and adds `AnalyserMeterConfiguration` and
`AnalyserMeter.configure()`. Configuration keeps the graph/ports intact and
does not reconfigure a borrowed analyser. `TransportGroup` now continues
natural-stop and loop monitoring when `driftCheckIntervalMs` is zero; zero
disables follower drift correction, not all lifecycle observation. Clockless
master reconciliation accounts for quantized position reports. Review custom
transport adapters against the [Kernel reference](../../platform/kernel/README.md).

UI retains its previous public subpaths and adds `./level-analyzer`,
`./spectrum-analyzer`, `./oscilloscope` and `./transient-analyzer`.
Playlist/recorder presenters add configuration and improve cleanup,
disabled-state handling and callback reentrancy. Surface sliders add gesture
notifications, cancellation and pointer modes. Applications with custom
bindings or styling should review the owning references in the
[UI component index](../COMPONENTS.md#ui-presenters) and use public tokens, parts and
handles.

## Before the publisher starts

Complete these steps on a reviewed release commit. The release PR targets
`main`; use `release/0.2.0` as its source branch. The maintainer's merge/review
and npm publication remain explicit actions.

1. Confirm all five manifests and intra-repository dependency ranges are
   `0.2.0` / `^0.2.0`, with the matching committed lockfile. Preparation uses
   `npm run release:prepare -- 0.2.0` then `npm install --package-lock-only`.
2. Complete the local gate and review CI for the exact commit to publish.
   A successful check on an earlier `0.1.0` source snapshot does not validate
   this candidate. If a PR merge changes the publishing SHA, validate that
   merged checkout and its CI before proceeding.
3. Review each tarball's exports, declarations, workers, README, project
   license and bundled third-party notices. Site demo media are not included
   in npm tarballs; website asset acceptance remains a separate requirement
   owned by STATUS and the [asset inventory](../../apps/doc/webmusic/ASSETS.md).
   CI builds the website on pushes and pull requests, but deploys only after
   an explicit manual dispatch on `main` with `deploy_pages` selected. Leave
   that option off while the eight media files' redistribution evidence remains
   unresolved; publishing the npm packages does not require site deployment.
4. Retain the historical Agent Toolkit `0.1.0` registry receipt. Source
   snapshot metadata may say `0.2.0`, but a new verified-release receipt must
   use the actual published artifacts after publication succeeds.

From the clean publishing checkout at the repository root:

```sh
git status --short
release_commit=$(git rev-parse HEAD)
git log -1 --format='%H %s'
npm ci
npm run check
npm run docs:build
npm run audit:production
npm run check:external-install
```

The status output must be empty. Stop on any failed command and resolve it
before publishing. Preserve the release SHA and command output with the
release record. Do not change source or rebuild concurrently with packaging.

## Authentication and fresh registry checks

Use the intended npm account and the public npm registry:

```sh
npm login --registry=https://registry.npmjs.org/
npm whoami --registry=https://registry.npmjs.org/
git tag --list v0.2.0
git ls-remote --tags origin refs/tags/v0.2.0 'refs/tags/v0.2.0^{}'
```

Confirm that account has publish rights to all existing `@webmusic` packages
and may create `@webmusic/audio` and `@webmusic/bridge`. Satisfy npm's current
authentication/2FA requirements. A successful identity query alone does not
establish those permissions.

Query every package's `versions` and `dist-tags` immediately before release:

```sh
for release_package in kernel ui score audio bridge; do
  npm view "@webmusic/$release_package" versions dist-tags --json --registry=https://registry.npmjs.org/
done
```

Resolve unexpected network or authentication errors before continuing. An
E404 from a public query does not establish scope ownership or permission to
create a package. If any `0.2.0` artifact or tag already exists, reconcile it
against the original release record before continuing. Never overwrite a
published version or move an existing tag. Changed artifacts need a new
shared version.

## Verify registry installation, then tag

After all five exact versions are visible, run a fresh registry install
outside the repository. This is a delivery smoke check in addition to the
earlier local-tarball external-install gate:

```sh
release_consumer=$(mktemp -d)
(
  cd "$release_consumer" || exit 1
  npm init -y >/dev/null || exit 1
  npm install --save-exact --registry=https://registry.npmjs.org/ \
    @webmusic/kernel@0.2.0 @webmusic/ui@0.2.0 @webmusic/score@0.2.0 \
    @webmusic/audio@0.2.0 @webmusic/bridge@0.2.0 || exit 1
  npm ls @webmusic/kernel @webmusic/ui @webmusic/score @webmusic/audio @webmusic/bridge || exit 1
  node --input-type=module -e 'for (const name of ["kernel", "ui", "score", "audio", "bridge"]) { await import("@webmusic/" + name); console.log("Imported @webmusic/" + name); }'
)
```

Keep its `package-lock.json` and registry responses with the release record.
This smoke check does not exercise audio devices or browser interactions.
When all delivery checks pass, return to the publishing checkout and confirm
the recorded SHA and tag state again:

```sh
git rev-parse HEAD
git status --short
git tag --list v0.2.0
git ls-remote --tags origin refs/tags/v0.2.0 'refs/tags/v0.2.0^{}'
```

Only when `release_commit` still identifies the validated publishing commit
and neither tag query finds `v0.2.0`, create the annotated tag there:

```sh
git tag -a v0.2.0 "$release_commit" -m 'v0.2.0'
git push origin v0.2.0
```

Preserve `v0.1.0`. Update the Agent Toolkit release receipt in a follow-up
change using verified `0.2.0` registry metadata and installed artifacts, then
regenerate and test its outputs. A manifest bump, local build, Git tag or
website deployment cannot substitute for those publication results.
