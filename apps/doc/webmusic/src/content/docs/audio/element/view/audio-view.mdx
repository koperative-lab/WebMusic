`<audio-view>` is the Audio **projection stage** — one element that draws decoded audio onto a canvas and follows a player. The three drawings are the *same* tag with a different `type` attribute (and the matching data property). Switching `type` at runtime disposes the old visualizer and re-renders; unknown values fall back to `waveform`.

| `type` | Draws | Needs |
| --- | --- | --- |
| **`waveform`** (default) | Min/max waveform with a playhead. | `.peaks` — an `AudioPeaks` pyramid from [`computePeaks`](/audio/api/analyze/), a `peaks-src` JSON file, a `.clip` or a bound player. |
| **`spectrogram`** | STFT magnitude heatmap (time × frequency). | `.spectrogram` — `SpectrogramData` from [`computeSpectrogram`](/audio/api/analyze/). |
| **`meter`** | Live RMS / spectrum level bars, with no time axis. | An `AnalyserNode`, tapped from the bound player. |

<AudioViewDemo />

The examples on this page share one decoded clip and peaks pyramid. The first
waveform does not wait for a spectrogram: spectra are prepared through the
analysis worker when a spectral mode is selected. The lower examples activate
when they approach the viewport or receive keyboard/pointer interaction, and
reuse their prepared data. Loading and failures appear beside the relevant demo.
The demos start in `drag-mode="scrub"`: the playhead stays centered while the
track moves underneath. Drag left toward later audio, or right toward earlier
audio. Their decoded player sounds the movement at your gesture speed, then
coasts in both position and sound before restoring its previous playing/paused
state. Parameters can switch
to viewport-only `pan`.

The main demo authors `height="96"` and `amplitude="1.6"` for a compact, fuller
waveform. This fixed visual gain can crop tall peaks; it changes neither PCM nor
playback volume. Parameters, copied markup and Reset use those authored values.
Switching drawing type retains the explicit height; the library defaults remain
128 px for waveform, 256 px for spectrogram and amplitude 1.

## Import

```html
<script type="module">
  import { defineAudioViewElement } from '@webmusic/audio/view/element';
  import { defineAudioPlayerElement } from '@webmusic/audio/play/element';
  defineAudioViewElement();
  defineAudioPlayerElement();
</script>

<audio-player id="p" src="/wav/Arabesque%20No.1.wav" controls></audio-player>
<audio-view id="v" player="#p" type="waveform" pixels-per-second="100" interactive drag-mode="scrub"></audio-view>

<script type="module">
  import { loadClipFromUrl } from '@webmusic/audio/play';
  import { computePeaks } from '@webmusic/audio/analyze';
  const clip = await loadClipFromUrl('/wav/Arabesque%20No.1.wav');
  const view = /** @type {import('@webmusic/audio/view/element').AudioViewElement | null} */ (document.getElementById('v'));
  const channels = clip.channels();
  if (view && channels) view.peaks = computePeaks(channels, clip.sampleRate);
</script>
```

`defineAudioViewElement(tag?)` registers the one element; `defineAllAudioElements()` (also from `@webmusic/audio/view/element`) registers all View tags at their default names. Import `@webmusic/audio/view/auto` to register on module evaluation, or `@webmusic/audio/view/global` for a prebuilt `<script>`-tag bundle.

## What each drawing needs

**Waveform** — the default. Give it a multi-resolution `AudioPeaks` pyramid and it draws a min/max waveform; with a bound `player` and `interactive`, it follows the playhead and turns clicks into `webaudio:seek`. Build the peaks once from the decoded channels with [`computePeaks`](/audio/api/analyze/):

```ts
const clip = await loadClipFromUrl('/wav/Arabesque%20No.1.wav'); // @webmusic/audio/play
view.peaks = computePeaks(clip.channels()!, clip.sampleRate); // @webmusic/audio/analyze
```

**Spectrogram** — a short-time Fourier transform drawn as a heatmap: time on the x-axis, frequency on the y, magnitude as colour. Feed it `SpectrogramData` from [`computeSpectrogram`](/audio/api/analyze/) (one channel in, column-major magnitudes out) and tune the look with `color-map`, `min-freq` and `max-freq`:

```html
<audio-view player="#p" type="spectrogram" color-map="viridis"></audio-view>
```

```ts
import { computeSpectrogram } from '@webmusic/audio/analyze';
view.spectrogram = computeSpectrogram(clip.channelData(0)!, clip.sampleRate, {
  fftSize: 1024,
  hopSize: 256,
});
```

This drawing is **precomputed only**: `src`, `peaks-src` and a bound player supply no spectrogram, so `.spectrogram` is the one way in. Until it is assigned the view says so — `No spectrogram to draw — assign .spectrogram` — instead of leaving a blank box, and draws normally as soon as the data arrives. Everything time-axis-shaped is exactly what a waveform gets: `player` + `follow` move the playhead, `interactive` seeks, `annotate` drags out regions, and `pixels-per-second` / `setZoom()` / `panTo()` / `visibleRange()` / `webaudio:viewportchange` are the same [one geometry model](#one-geometry-model).

**Meter** — a live RMS-level (or `spectrum`) meter. It has no time axis and needs no precomputed data — instead it taps the **`AnalyserNode` of the player it is bound to**, reading it every animation frame. Resolution is structural: `<audio-view type="meter">` reads `.analyser` off the element named by `player="#id"` (or off that element's `.player`), so the target must expose an `AnalyserNode` — an [`AudioClipPlayer`](/audio/api/play/) has one at `.analyser`. **A meter only moves while audio is flowing — press play to see it react.**

```html
<audio-player id="p" src="/wav/Arabesque%20No.1.wav" controls></audio-player>
<audio-view player="#p" type="meter" mode="level"></audio-view>
```

With no analyser to read, the view shows the shared square waiting animation with an accessible source description; binding a player that has one draws it immediately.

:::note
There are two meter surfaces. The `meter` **type** above is a passive drawing
of the consolidated `<audio-view>` element; the standalone
[`<audio-meter>`](/audio/element/analyze/audio-meter/) is a compact live Analyze
monitor with its own analyser/context wiring and needs no view host. Its former
`view/element` registration remains available for compatibility.
:::

:::caution[Instantaneous, not historical]
A meter shows the level **now**. It has no time axis, no playhead, no seek and no viewport, so it cannot show what happened a second ago. For a scrolling history of a live signal — waveform or spectrogram — use [`<audio-live-view>`](/audio/element/view/audio-live-view/). For a triggered inspection of the current sample window, use [`<audio-oscilloscope>`](/audio/element/analyze/audio-oscilloscope/).
:::

When bound to `<audio-player>`, the view reads its resolved clip immediately
and refreshes on `webaudio:sourcechange`, including borrowed-player replacement
and clearing. `webaudio:loaded` remains supported for legacy graph-ready event
sources. Rebinding releases the old subscriptions; the view never disposes its
borrowed player. Explicit `.clip` / `.peaks` or loaded View data takes precedence
over borrowed data.

## Three ways in

```html
<!-- 1. Decode: the element loads and decodes through @webmusic/audio/play -->
<audio-view type="waveform" src="/wav/Arabesque%20No.1.wav" interactive></audio-view>

<!-- 2. No decode: BBC audiowaveform v2 JSON, hydrated straight into the pyramid -->
<audio-view type="waveform" peaks-src="song.json" interactive></audio-view>

<!-- 3. Bring your own: a player supplies the clip, or you assign .peaks -->
<audio-player id="p" src="/wav/Arabesque%20No.1.wav" controls></audio-player>
<audio-view player="#p" type="waveform" interactive pixels-per-second="100"></audio-view>
```

`peaks-src` is the path that draws a long file with **no decode at all**: no `AudioContext`, no samples and no `@webmusic/audio/play` import. Its duration comes from the pyramid, since there is no clip to ask. A failed request surfaces as `webaudio:error`; while either loader is in flight the element carries `aria-busy`.

## Dragging and seeking

`drag-mode` chooses how a pointer drag behaves on a waveform or spectrogram.
The element default is `seek`; these demos explicitly select `scrub`.

| `drag-mode` | Drag behavior | Requires |
| --- | --- | --- |
| `seek` (default) | Seek continuously to the absolute time under the pointer. | `interactive` |
| `scrub` | Keep the playhead centered and move the track: left advances, right reverses. A supported player pauses normal playback and sounds the movement at gesture speed. Release coasts in position and sound, then restores its previous playing/paused state. | `interactive`; decoded PCM and a scratch-capable player for sound |
| `pan` | Move the visible window without changing the playback position. Left reveals later audio; right reveals earlier audio. | `scrollable`; works without `interactive` or a player |
| `none` | No drag action. Click and keyboard seeking remain available. | `interactive` for seeking |

```html
<audio-view player="#p" interactive drag-mode="scrub"></audio-view>
<audio-view peaks-src="song.json" drag-mode="pan"></audio-view>
```

With `interactive`, `seek`, `scrub` and `none` retain click and keyboard seeking.
In `pan`, pointer and keyboard input operate only the viewport: a click does not
seek. `annotate` takes priority over every drag mode; a meter ignores `drag-mode`.
An absent or unrecognized value falls back to `seek`. The matching JavaScript
property is `view.dragMode`; its `AudioViewDragMode` union is exported from
`@webmusic/audio/view/element`.

With annotation off, `pan` suspends auto-follow for the entire mode so playback
does not pull the window away from the place being inspected. `scrub` uses a
fixed center playhead independently of `follow` and `scrollable`, even at zero
or the clip's end. Blank space fills the area outside the clip. Hit-testing that
padding clamps to zero/end; `visibleRange()` reports only the real clip portion.
Native panning and `panTo()` are ignored while centered; choose `pan` to browse another window.

### Audible scratch support and fallback

For a bound player exposing `beginScratch()`, pointer press borrows a scratch
session. The native decoded player suspends normal playback and maintains
continuous forward/reverse audio through bounded PCM windows on its existing
volume, pan and effect route. Left means forward; right means reverse; speed and
pitch follow movement. Holding still brakes scratch output and does not keep
normal playback running. This is sample-speed scratching, not pitch-preserving
time stretching.

Normal release applies the final coordinate, then coasts for about 280 ms on the
player's AudioContext clock. Position and sound transition together from the
signed release speed toward the configured playback rate for a previously
playing source, or toward zero for a paused source. Ordinary playback resumes
only after that transition; a paused source settles to rest. A stationary click
changes position silently and restores directly. Releasing after motion has
stopped does not reuse an old fling velocity.

The View retains the session through release inertia so another press can take
over while preserving the original playing intent. Cancellation (pointer cancel,
lost capture, blur, mode/zoom/source change or removal) stops it without resuming,
including after pointer release. A later transport command or replacement source
invalidates older session work so late readiness cannot restart it. Rendering
follows the player's accepted position throughout; it has no separate momentum
animation or scratch clock.

The capability is optional. A legacy player without `beginScratch()`, or a player
that returns no session because decoded PCM is unavailable, keeps position-only
scrubbing. It does not promise scratch sound, release inertia or playback-state restoration; the
unsupported request itself has no player side effects. `pan` never needs this
capability. A failed supported session is reported through `webaudio:error`.
See [AudioClipPlayer scratch sessions](/audio/headless/play/audio-clip-player/#scratch-sessions)
for the public nonvisual API; the existing `scrub(deltaSeconds)` method remains
a relative seek helper.

## Annotate

`annotate` connects drag-to-create. A drag across the surface creates a `Region` and the element emits `webaudio:regionchange` carrying its **whole** region list — the ones it already had plus the new one, so a first drag can never silently drop a clip's existing regions:

```html
<audio-view id="v" type="waveform" src="/wav/Arabesque%20No.1.wav" annotate></audio-view>
```

```ts
v.addEventListener('webaudio:regionchange', (event) => {
  clip = clip.withRegions(event.detail.regions);   // detail.regions is the whole list
});
```

`annotate` overrides `drag-mode`, including `none` and `pan`. With `interactive` as well, a **click** seeks and a **drag** draws a
region; dragging a region neither seeks nor pans the viewport. The element owns the
whole gesture in that mode — the kit's slider is already capturing the pointer on that node, so the
drag-to-create path is not bound a second time.

Editing existing regions is deliberately **not** part of this contract — only creation. A created region carries an empty label, so an index shows its id until you name it. Annotation needs no player: the drag path binds for `annotate` alone.

## One geometry model

Zoom, offset and the visible window live in **one** headless `AudioTimeline` the element owns, kept in step with what the renderer actually painted. `zoom`, `visibleRange()` and `panTo()` therefore use the same numbers the surface is drawn from:

```ts
view.visibleRange();            // { startSeconds, endSeconds } — or undefined
view.panTo(30);                 // scroll so the window starts at 0:30
view.setZoom(240);              // live re-zoom, keeping scroll + playhead
view.zoom;                      // the scale actually drawn at — never 0
view.addEventListener('webaudio:viewportchange', (event) => {
  const {startSeconds, endSeconds} = event.detail;
});
```

`webaudio:viewportchange` fires once per distinct window, for a user pan (scrollbar, wheel or drag) and a programmatic `panTo()` / `setZoom()` alike — the first paint is not a pan, and putting a window back after an in-place repaint is not one either.

### Playback presentation cadence

With a live player exposing `seconds` (or `currentTime`) and optional `playing` /
`scratching` state, the view reads the borrowed position on visible display
frames. The renderer, timeline, slider value and viewport follow that same read,
including scratch release inertia. Unchanged positions skip repainting; paused
changes still update, hidden pages stop frame observation, and reappearing views
read the current player position. The terminal reset to zero survives visibility
changes until a new time update. No visual clock or predicted position is added.

Legacy event-only targets keep their `webaudio:timeupdate` cadence. For example,
the native player's default event interval is 50 ms, while its live getters let
the view observe movement between those events.

## Loading and waiting feedback

Each `type` mounts the shared `@webmusic/ui/status` presenter when its data is missing.
An active `src` or `peaks-src` request shows the loading animation. When using borrowed
player data, source loading and failure follow the player's `.loading`, `.loadError` and
`webaudio:loadstatechange` contract. Explicit view data keeps its independent presentation. Otherwise a quiet square
waiting animation replaces visible placeholder prose; the following descriptions remain
available to assistive technology:

| `type` | Accessible description |
| --- | --- |
| `waveform` | `No audio to draw — assign .clip or .peaks` |
| `spectrogram` | `No spectrogram to draw — assign .spectrogram` |
| `meter` | `No analyser to meter — bind a player with an analyser` |

A failed `src` or `peaks-src` request shows its error message when no drawable data
is available, while still emitting `webaudio:error`. Retrying, removing that URL,
or replacing that input with `.clip` / `.peaks` clears that input's failure. The
two URL inputs keep separate loading and error state; a pending alternative source
continues to show loading, and stale requests cannot overwrite newer feedback.
Assign the missing data and the view draws.

<summary>API</summary>

Renderer paint and geometry options are exposed as kebab-case HTML attributes and camelCase fields on `.options`. Element interaction settings use their own properties: `interactive`, `dragMode`, `annotate`, `follow` and `scrollable`; `dragMode` does not belong in `.options`. Attribute parsing is NaN-/empty-safe — an absent, empty or non-numeric value falls back to the default rather than poisoning the render; tri-state booleans read `false` / `0` / `no` / `off` as false and anything else present as true. Where both an attribute and `.options` are set, **`.options` wins**.

Members that only apply to one drawing are marked in the Description; everything else works under every `type`.

```ts
const view = document.querySelector('audio-view');
view.peaks = computePeaks(clip.channels(), clip.sampleRate); // draw a waveform
view.zoom = 200;                                             // live zoom (keeps scroll + playhead)
view.follow = false;                                         // stop auto-scrolling with playback
view.scrollable = false;                                     // disable scrollbar/wheel and pan-mode dragging
view.interactive = true;                                     // click + keyboard seeking
view.dragMode = 'scrub';                                     // centered track + optional scratch sound
view.options = { amplitude: 1.3, virtualization: { bufferScreens: 2 } }; // advanced bag
view.type = 'spectrogram';                                   // switch the drawing live
```

**Events** — all `{ bubbles, composed }`

| Event | Detail | Fires when |
| --- | --- | --- |
| `webaudio:seek` | `{ seconds, region? }` | Keyboard input, ordinary clicks and absolute `seek` dragging announce requested clip seconds **before** the bound player's seek command. This includes clicks in `seek`/`none`, annotation clicks and position-only `scrub` fallback clicks. A click using a supported scratch session moves silently and emits **after** the command, as does a relative `scrub` drag; these report accepted clip seconds when readable. Keyboard input cancels any held scratch gesture before ordinary seeking. `pan` never emits this event. `region` is present when the seek hit-test identified one. A bound player announces its own transport seeks itself; this element never re-emits those. |
| `webaudio:regionchange` | `{ regions }` | An `annotate` drag created a region. `regions` is the element's **whole** list, not just the new one. Nothing else emits it. |
| `webaudio:viewportchange` | `{ startSeconds, endSeconds }` | The visible window moved — user pan or zoom, and programmatic `panTo()` / `setZoom()` alike. Once per distinct window; the first paint is not a pan. |
| `webaudio:error` | `{ error }` | A `src` or `peaks-src` load, or a render, failed. |

**The meter is the exception.** It reads no precomputed data — it samples the analyser every animation frame, borrows that node and never disposes it. The time-axis members do nothing there, and do nothing quietly: `visibleRange()` returns `undefined`, `panTo()` moves nothing and announces no `webaudio:viewportchange`, click-to-seek is never wired, and the drag binding is not created at all — so `annotate` and `drag-mode` have no effect and `webaudio:regionchange` cannot fire. `webaudio:error` is the one event left.

**Accessibility.** An `interactive` surface — waveform or spectrogram — is a `role="slider"` named `Audio position`, with `tabindex="0"` and live `aria-valuemin` / `aria-valuemax` / `aria-valuenow` in seconds; `←` / `→` step by a hundredth of the duration (at least one second) and `Home` / `End` jump to the ends. In `drag-mode="pan"` with annotation off and `scrollable` enabled, the slider is instead named `Audio viewport` and its value is the window start: arrows move a quarter-window (minimum 0.05 seconds), Shift+arrows move a whole window, and Home/End move to the first/last window. It works without `interactive`; no pan key seeks playback. Display-only, a waveform is a `role="img"` named `Audio waveform` and a spectrogram a `role="img"` named `Audio spectrogram`. A rendered meter is a `role="group"` labelled `Audio level meter` — a group rather than an `img` so the presenter's own `role="meter"` stays exposed to a screen reader. Your own `role`, `aria-label`, `aria-labelledby` or `tabindex` is never overwritten, and anything the element assigned is removed again when it no longer applies.

`.clip` returns the clip assigned to this Element, and `.peaks` returns assigned
or fetched peaks. These getters do not publish the player-borrowed clip or
internally derived peaks.

**Subclassing.** `AudioViewElement` exposes four protected hooks: `createTimeline()` (seed a subclass's own geometry — a fixed window, a shared one), `renderOptions()` (add or override options without re-implementing the attribute mirroring), `renderStage()` (render another visualization while keeping the stage, binding and accessibility) and `onViewError()` (the one observable failure channel).

The placeholder shown when there is no data is the kit's `role="status"` presenter. A standalone status presenter keeps its own full surface.

## Dressing the same peaks

Every knob is an HTML attribute, so the *same* peaks can be dressed many ways — recolour the columns, make it taller and zoom in, give the inner canvas a dark fill, or map the colours through a palette. These four share one decoded clip:

```html
<!-- recoloured -->
<audio-view type="waveform" wave-color="#22c55e" progress-color="#15803d" playhead-color="#f59e0b"></audio-view>
<!-- taller, zoomed in, gain-boosted -->
<audio-view type="waveform" height="180" pixels-per-second="240" amplitude="1.3"></audio-view>

<!-- colour-mapped (needs .frequencyData) -->

```

For frequency-tinted **multi-band** colouring, **split** stereo, channel selection (L/R/M/S) and a **history** glow, see [Colour modes](#colour-modes).

## Colour modes

The waveform's **shape** is always the amplitude peaks, but its **colour** can read the audio's frequency content — the `color-mode` attribute works like a multi-band meter:

- **`static`** (default) — one flat colour (`wave-color` / `progress-color`).
- **`multiband`** — each column is tinted by its spectral balance: bass → red, mids → green, treble → blue, blended additively (so a bass-and-air column reads magenta, a full-range hit reads white). `bands` sets the band count (default `3`, clamped 1–12).
- **`colormap`** — each column's spectral centroid is mapped through `color-map` (`viridis` · `magma` · `grayscale` · `gray`).

The two frequency modes need STFT data (from [`computeSpectrogram`](/audio/api/analyze/)) computed from the **same channel** as the `.peaks`. Assign it to `.frequencyData` — a first-class property — or to `.spectrogram`, which is the same payload seen from the other mode's point of view. The resolution order is `.options.frequencyData`, then `.frequencyData`, then `.spectrogram`. Two more knobs complete the meter feel: `channel-layout="split"` stacks the first two peaks channels as a stereo display (each half coloured by its own spectrum, from a `.frequencyData` array), and `history` glows a recent-history window that trails the playhead during playback. The demo caches peaks + spectrogram on first request per channel for Left / Right / Mid / Side (Channel 1 and an optional Channel 2), and flips `color-mode` / `history` live:

<MultibandWaveformDemo />

```html
<audio-view type="waveform" color-mode="multiband"></audio-view>
```
```ts
view.peaks = computePeaks([channel], sampleRate);                 // shape
view.frequencyData = computeSpectrogram(channel, sampleRate, {}); // colour source
view.setAttribute('color-mode', 'multiband');                     // bass→red · mid→green · treble→blue
```

| Member | Kind | Description |
| --- | --- | --- |
| `color-mode` | attribute | `multiband` or `colormap` (default `static`). |
| `bands` | attribute | Band count for `multiband` (default `3`, clamped 1–12). |
| `channel-layout` | attribute | `split` stacks L/R with per-channel spectra. |
| `history` | attribute | Playhead glow window in seconds. |
| `.frequencyData` | property | The STFT the two frequency modes read; an array colours a `split` display per channel. |

Multiband mode tints columns additively; `history` dims columns outside the trailing window. All other colour knobs are the ordinary waveform paint attributes in the Styling block above.
