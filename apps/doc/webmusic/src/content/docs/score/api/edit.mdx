Score Edit applies semantic note operations to immutable Scores. Its pure
function supports application-owned state; its `ScoreEditor` facade adds one
document owner, revision guards, local history and interaction drafts. It creates
no player, clock, loader or DOM surface.

Install `@webmusic/score` as described in [Install](/score/#install). Edit needs
no optional UI, framework or audio-engine peer. The code entries remain
nonvisual; the [document Element](/score/element/edit/score-document/) owns HTML
loading, while [Score player](/score/headless/play/score-player/) and
[Score view](/score/element/view/score-view/) borrow the shared Core ports.

## Atomic note operations

`applyScoreOperations(score, operations)` returns a candidate `score`, a
defensive immutable snapshot of `operations`, and `affectedNoteIds`: the notes
the batch inserted, removed or changed relative to the input, in first-touched
order. A note inserted and deleted, or changed and restored, within the batch
is not listed; a net-zero batch returns the input Score and no IDs. Operations
run in order; invalid input throws `ScoreEditError` without modifying the source.
The helper has no document identity, revision, history or subscriptions. Use
`ScoreEditor.execute` when the operation must also commit to an owned document.

Every operation has the following exact fields. IDs refer to authored notes,
not repeat-expanded playback occurrences. Insertions supply their own stable IDs.

| `type` | Fields | Meaning |
|---|---|---|
| `insert-notes` | `notes: ScoreNoteInput[]` | Add notes to existing parts. Each input has `id`, `partId`, written `pitch: {step, alter, octave}`, `onsetQuarters`, `durationQuarters`, `voice`, and optional `velocity`. |
| `delete-notes` | `noteIds` | Remove the named notes. Tied, tuplet and grace notes reject as `unsupported-structure` even when the whole chain or group is named; deleting only part of an authored slur pair or beam group also rejects. |
| `move-notes` | `noteIds`, `deltaQuarters` | Shift written onset by exact rational quarters, retaining Duration notation. |
| `resize-notes` | `noteIds`, `durationQuarters` | Set a positive exact quarter duration for simple notes. |
| `transpose-notes` | `noteIds`, `semitones` | Transpose written pitch by an integer number of semitones, respelled as described below. |
| `set-velocity` | `noteIds`, `velocity` | Set integer velocity 1–127; rests and tie continuations reject. `null` clears the authored override. |
| `quantize-notes` | `noteIds`, optional `grid`, `origin`, `target` | Snap onset, duration, or both to a rational grid. Defaults: grid `[1,4]`, origin `[0,1]`, target `'onset'`; ties round forward. |
| `enter-notation` | `entry: ScoreNotationEntry` | Enter a spelled note or rest in one existing measure and one voice/staff, replacing fully covered events and filling remaining gaps with written rests. |

`ScoreQuarterValue` is a reduced safe-integer `[numerator, denominator]` pair
with positive denominator. Onsets cannot become negative and ordinary-note
durations must remain positive. Invalid/unknown IDs, duplicate insertion IDs,
unsupported operation fields or structures reject the whole batch. Commands do
not repair partial ties, tuplets or grace notation. Only `enter-notation` fills
the selected measure/voice/staff with written rests; ordinary piano-roll
operations retain their event-editing behavior.
Insertion, transposition and notation entry require a written MIDI pitch of
0–127 and, after adding the Part transposition (`chromatic + 12 × octaveChange`),
the sounding pitch 0–127 that playback and MIDI export use. Transposition
rejects tied, rest and unpitched notes. A numeric `set-velocity` rejects rests
and tie continuations, the later notes of a tie chain. Playback and MIDI export
sound each tie chain once with its first note's velocity, so set that note
instead. `null` may clear any stored override. Quantization origin affects
onset only; duration quantization uses origin zero, and a duration rounded to
zero rejects.

Transposition by a multiple of 12 semitones keeps the written step and
accidental and changes only the octave: `Bb4` becomes `Bb5`, and `E#4` becomes
`E#5`. Other intervals spell the resulting pitch by the original accidental
direction. A note spelled with a flat keeps flats (`Bb4` + 3 is `Db5`); a
natural or sharp note uses sharps (`D4` + 1 is `D#4`); white keys are naturals
(`Eb4` + 1 is `E4`). These results never contain double accidentals and do not
consult the key signature.

Resize, duration quantization and insertion store a written Duration for the
exact quarter length. A length spelled by a whole through sixty-fourth base
with zero to two dots uses that spelling: `[3,4]` is a dotted eighth and `[7,8]`
a double-dotted eighth. Any other length, such as `[5,4]` or `[1,3]`, becomes
its own base with no dots and has no single-note staff spelling. A move keeps
the existing Duration.

Deletion keeps authored slurs and beams matched. A slur's `start` and `stop`
endpoints pair by voice and slur number; a level-one beam group runs from
`begin` through `end` in one voice and staff, with chord members sharing their
onset. Delete such a pair or group entirely, or not at all; a partial deletion
fails with `unsupported-structure`. Unmarked notes inside a slur can be deleted
individually, and already unmatched marks are not protected.

An effective move, resize or quantize makes written time authoritative for each
changed note: it removes absolute `performed` timing and retains the prior
effective velocity in `velocityOverride`. Sounding duration follows the new
quarter endpoints through the TimeMap, including interior tempo changes.
Pitch-only, velocity-only and no-op timing operations preserve performed timing;
untouched notes retain imported microtiming. Effective velocity is
`velocityOverride ?? performed?.velocity ?? 80`.

Quantization compares written time only. A note whose written onset and
duration already lie on the grid is unchanged and keeps its `performed` timing.
For example, [Score Recorder](/score/element/play/score-recorder/) output
with a nonzero `quantize` already has grid-aligned written time. Quantizing it
to that grid is a no-op, and playback and MIDI export continue to use its exact
performed timing.

This standalone example creates an explicit input and computes a candidate:

```ts
import {Duration, NoteId, PartId, Pitch, Rational, ScoreBuilder, VoiceId} from '@webmusic/score';
import {applyScoreOperations} from '@webmusic/score/edit';

const partId = PartId('piano');
const noteId = NoteId('opening-note');
const builder = new ScoreBuilder();
builder.addPart({id: partId, name: 'Piano', midiProgram: 0, staves: 1});
builder.addNote(partId, {
  id: noteId, pitch: Pitch.parse('C4'), onsetQuarters: Rational.ZERO,
  duration: Duration.quarter(), voice: VoiceId('melody'),
});
const original = builder.build();
const result = applyScoreOperations(original, [
  {type: 'move-notes', noteIds: [noteId], deltaQuarters: [1, 4]},
  {type: 'set-velocity', noteIds: [noteId], velocity: 96},
]);
console.log(original.getNote(noteId)?.onsetQuarters.toString()); // 0
console.log(result.score.getNote(noteId)?.onsetQuarters.toString()); // 1/4
```

## Written notation entry

`enter-notation` uses `ScoreNotationEntry`: a new `id`, existing `partId`,
`voice`, optional one-based `staff`, `onsetQuarters`, `duration`, and `pitch`.
`pitch` is the same spelled `{step, alter, octave}` as ordinary note insertion;
`null` enters a rest. Optional `velocity` sets a pitched note's authored
velocity. `ScoreNotationDuration` has `base: ScoreQuarterValue` and optional
`dots` (default `0`); supported bases are whole through sixty-fourth notes
(`[4,1]` through `[1,16]`), with zero, one or two dots. These are notation
values, so the sounded duration includes their dots.

Entry requires an existing positive authored measure containing the complete
duration. It does not infer measures from a MIDI time signature or extend the
piece. The selected measure/voice/staff must be simple and monophonic. Fully
covered notes are replaced; an overlap that would cut a sounding note is
rejected. Existing rests may be split, and remaining gaps become actual rests
with deterministic IDs and written durations. Other voices and staves remain
unchanged. Automatic completion requires exact gaps on a 1/64-quarter grid and
generates at most 256 rests per operation. It can use smaller rest values than
the offered input bases. One entry, including rest repair, is one atomic
operation. A controller entry commits one history item; a transaction containing
several entries shares one item, and the pure helper creates no history.

Ties, tuplets, grace notes, chords, authored beams, slurs, hidden or unpitched
notation, events crossing a measure boundary and unrepresentable rest gaps
are outside this entry subset. Replacing events with articulations, ornaments,
dynamics, lyrics or tags also rejects rather than discarding them. These
structures fail explicitly instead of silently losing notation. Stem
directions, rest positions and tie placement are display hints; a replacement
does not keep them. An entry whose result matches the replaced events apart
from generated IDs, such as re-entering an existing rest with its duration, is
a no-op. It keeps the existing notes, their IDs and any selection.

The [staff input controller](/score/headless/view/staff-editing/) supplies
cursor, duration and voice state for a custom interface over this same
operation; it does not create another Score or history.

## Document ports and commands

`ScoreDocumentSource` exposes `getSnapshot()` and synchronous `subscribe`.
`ScoreEditorPort` adds state, commands, history and interaction-session creation.
These interfaces live in Core so another capability can read a document without
depending on the editor implementation. Native ScorePlayer accepts the read-only
port; editable Score views require the command/session port.

`isScoreDocumentSource(value)` checks the required reader/subscriber methods and
the current snapshot: nonempty document/content identity, a nonnegative safe
revision, `ready` or `disposed` status and a Score instance. `isScoreEditorPort`
also checks every required state, command, history and session method. Both
return `false` for malformed values or throwing getters. These structural type
guards do not subscribe, mutate, or establish readiness: a disposed source can
satisfy the port shape, so consumers still inspect its snapshot status.

A `ScoreEditCommand` carries `version: 1`, `documentId`, `expectedRevision`,
`label` and `operations`. `execute` validates the complete serializable envelope
and commits atomically. `ScoreEditResult` is `committed` with a snapshot/change,
`noop` with the unchanged snapshot, or `failed` with a `ScoreEditError`. Command
errors are results; the pure helper throws. The [ScoreEditor reference](/score/headless/edit/score-editor/)
owns revision, subscription, checkpoint and disposal details.

`ScoreDocumentSnapshot` contains `documentId`, `documentRevision`, `contentId`,
`content`, `status: 'ready' | 'disposed'`, and optional last `change`.
`ScoreDocumentChange` contains `origin`, `label`, from/to revisions, operations,
affected note IDs and a position map. Undo/redo/restore changes identify their
origin and do not replay the original edit operations.

## Position maps

Position maps describe content transitions in rational musical quarters. They
do not seek or reschedule a player.

| Function | Contract |
|---|---|
| `createScorePositionMap(documentId, fromRevision, toRevision, extent, policy?)` | Create a frozen map. Revisions are nonnegative safe integers with `toRevision > fromRevision`; `extent` is a nonnegative `Rational`. Policy defaults to `'preserve-quarter'`; `'reset-origin'` explicitly resets. |
| `composeScorePositionMaps(...maps)` | Require a nonempty, continuous revision chain for one document. Preserve intermediate clamps so an undo cannot reconstruct a lost position. The composed representation is bounded independently of undo history. |
| `mapScorePosition(map, position)` | Accept a nonnegative `Rational`; return `{quarters, clamped, positionPolicy}`. Preserved positions clamp to extent; reset policy returns the origin. |

Malformed maps or positions throw `ScoreEditError('invalid-command', ...)`.
A mismatched document or discontinuous composition throws `revision-conflict`.
The document source publishes maps with changes; consumers retain or compose
them themselves rather than expecting the editor to retain an unbounded log.

```ts
import {Rational} from '@webmusic/score';
import {createScorePositionMap, composeScorePositionMaps, mapScorePosition} from '@webmusic/score/edit';

const shorter = createScorePositionMap('example', 0, 1, new Rational(2));
const restored = createScorePositionMap('example', 1, 2, new Rational(4));
const result = mapScorePosition(composeScorePositionMaps(shorter, restored), new Rational(3));
console.log(result.quarters.toString(), result.clamped); // 2, true
```
