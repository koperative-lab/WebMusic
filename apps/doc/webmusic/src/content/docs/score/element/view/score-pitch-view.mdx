`<score-pitch-view>` shows the currently held notes from one player or structural note source. Choose `type="keyboard"` (default), `staff` or `fretboard`; every type shares the same note state and owns no playback resources. Use the type switch above the demo to see each one while the piece plays.

Without a resolved input, the view shows the shared outlined-square waiting
animation. A native source that is loading shows the four-square loading animation;
source errors remain visible. A ready source with no held notes keeps its normal pitch
surface; on the staff and fretboard its empty sentence (such as “No sounding notes”) is a
polite status that is visually hidden, so the empty drawing is the visible state. These states borrow the existing source subscription
and never create another player or clock. Descriptions remain available to assistive
technology; reduced-motion preferences stop the animation.

## Import

```html
<script type="module">
  import {defineScorePlayerElement} from '@webmusic/score/play/element';
  import {definePitchViewElement} from '@webmusic/score/view/element';
  defineScorePlayerElement();
  definePitchViewElement();
</script>

<score-player id="piece" src="/midi/Arabesque%20No.1.mid"></score-player>
<score-pitch-view input="#piece" type="keyboard"></score-pitch-view>
```

The demo contains one player and one pitch view in its default type. Attributes that apply to one type are retained, and ignored, while another type is shown.

## Ports and composition

`<score-pitch-view>` is a **View** companion. It declares no ports and provides no module
context to children. It borrows the held notes and playback state of one Score playback owner — a
`<score-player>` or a `<score-rack-part>` — and sends no transport commands. It
never registers with or creates a Session.

| Connection | Form | Behavior |
| --- | --- | --- |
| Containment | Nested inside a player or Rack part | Borrows the nearest one; no attribute needed |
| Explicit input | `input="#id"` | One unique element in the same Document or ShadowRoot |
| Explicit module | `.inputModule = module` | Follows that module's `source` port (`webmusic.score`), or the one `port` names; `null` unbinds |
| Module port | `port="source"` with `input` or containment | Follows the named source port on the selected or enclosing module instead of the owner element |
| Note events | `input="#id"` on a note source | Any element dispatching `webscore:noteon` / `webscore:noteoff`, such as [`<score-note-input>`](/score/element/play/score-note-input/) |

Playback resolves `.inputModule`, then the explicit selector, then containment, then nothing; a `port` attribute moves the selector or containment onto that module's source port. Views and analysis share one follower, so they see the same notes, position and readiness. An
`input` that is missing, invalid or ambiguous stays unbound, reported by
`data-player-state`, and never falls back to the enclosing scope. Inside a
source-free outer player, nest the view in the member that plays or name that
member with `input`. The view has no `src` or `.score`.

```html
<score-player src="/midi/Arabesque%20No.1.mid">
  <score-pitch-view type="keyboard" low="48" high="84"></score-pitch-view>
</score-player>
```

## Data and lifetime

An `input` selector must match exactly one target in the current Document or ShadowRoot; without one, the view follows the enclosing player or Rack part. Native snapshots initialize held notes; note and state events reconcile them after pause, seek, stop, end and source replacement. Late/replaced targets and containment scopes are rebound; invalid or ambiguous selectors remain unbound and never fall back to containment. Overlapping occurrences of the same MIDI pitch are counted, so releasing one does not erase another.

The component has no `src`, `.score`, note command or transport command. Changing `type` replaces only the presentation and keeps the current held-note state. Disconnect releases its observer, subscriptions and presenter without stopping the player. To enter notes, use [`<score-note-input>`](/score/element/play/score-note-input/).

## Keyboard

`type="keyboard"` shows requested MIDI endpoints `low="48"` through `high="71"`
(C3–B4) by default and fits the entire range into its container without
pitch-axis scrolling. The getters report rounded requested endpoints; the presenter normalizes them to MIDI 0–127, orders reversed endpoints and limits the displayed span to 88 semitones. Notes outside the displayed range remain in `.active`. Released keys clear without a visual release trail.

Set `scroll="true"` to allow scrolling along the pitch axis. In that mode, use
`white-key-width` and `black-key-width` for exact pixel pitch breadths; a narrower host
scrolls instead of compressing keys. With neither width set, the keyboard uses
responsive sizing with a readable minimum key width. Black width
defaults to `0.62 × white width`; setting black width alone derives white width
by dividing by `0.62`. These breadths run horizontally for `up`/`down`,
and vertically for `left`/`right`. Use `white-key-height` and `black-key-height` for key
depths in any direction. Black width and height cannot exceed white dimensions.

Set `scroll="false"` to fit the complete normalized range again. Fitting
overrides explicit key widths and the CSS minimum key width, using the default
`0.62` black/white width ratio. It retains the width attributes for the next
scrolling configuration. Key heights and held notes stay unchanged.

The legacy `fit-to-width` attribute is still accepted when `scroll` is absent:
`true` fits the range, while `false` enables scrolling. Explicit `scroll` always
takes precedence. Removing both attributes restores the default fit. New
configurations should use `scroll`. Without `scroll`, a retained legacy value
or the default applies; an explicit `scroll` value overrides it.

`follow="active"` reveals newly sounding pitches when scrolling is enabled.
The requested follow mode stays `active` by default, but fitting does not scroll.
Use `follow="none"`
when a shared application container should pan the keyboard together with a
[`waterfall`](/score/element/view/score-view/#align-a-waterfall-and-keyboard).

## Four keyboard directions

`direction` selects the key fronts: `down` (default), `up`, `left` or `right`.
An up/down keyboard lays pitches out from low at the left to high at the right;
a left/right keyboard lays them out from low at the bottom to high at the top.
Black keys stay between their natural neighbours, and labels stay upright.
Staff and fretboard retain their normal orientation.

For `left`/`right`, give the host a CSS height, for example
`style="height: 320px"`; that height is the available pitch axis. Fitting uses
it while fixed-width configurations can scroll vertically. Key-height
attributes still mean key depth, now horizontal. Direction changes preserve
held-note counts and the existing player binding.

Compose separate keyboards at either edge of a
[four-direction waterfall](/score/element/view/score-view/#align-a-waterfall-and-keyboard),
using matching MIDI endpoints and natural/accidental breadths, no presenter
insets, and one shared pitch-axis scroller. Several keyboards can borrow the
same player without another clock. Use the waterfall renderer for exact piano
key alignment; the piano-roll renderer has equal semitone lanes.

## Staff

`type="staff"` places current pitches on a `grand`, `treble` or `bass` staff. This is a sounding-pitch readout. To read notation over score time, choose [`<score-view type="staff">`](/score/element/view/score-view/#staff); for full engraving use [`<score-sheet-view>`](/score/element/view/score-sheet-view/).

## Fretboard

`type="fretboard"` marks every exact-MIDI location in the selected fret window. It does not choose a playable fingering or infer a chord voicing. Open-string tuning order is preserved, including reentrant instruments. Notes outside the window remain in `.active`; when none fit, the view reports “No sounding pitches in this fret range”.

`fret-width` sets the distance between fret wires, `string-spacing` sets the
distance between strings, and `string-width` sets their line thickness, all in
pixels. Explicit fret spacing remains fixed when the container grows and pans
when it does not fit. String thickness remains independent of the viewport
scale. Omit these attributes to retain density-based, responsive defaults.

| `white-key-width` | fit the range; responsive when scrolling | Keyboard | Fixed natural-key pitch breadth in px when scrolling is enabled; ignored while fitting. |
| `black-key-width` | `0.62 × white width` | Keyboard | Fixed accidental-key pitch breadth in px, capped at white width; alone derives white width as `value / 0.62`. Ignored while fitting. |
| `white-key-height` | theme height | Keyboard | Natural-key depth in px, perpendicular to pitch. |
| `black-key-height` | theme proportion | Keyboard | Accidental-key depth in px, capped at white-key height. |
| `fret-width` | responsive | Fretboard | Fixed distance between adjacent fret wires in px. |
| `string-spacing` | density geometry | Fretboard | Distance between adjacent strings in px. |
| `string-width` | density stroke | Fretboard | String stroke thickness in px, independent of viewport scaling. |

`.type` and `.direction` are writable reflected properties with types
`PitchViewType` and `PitchViewDirection`, exported by `@webmusic/score/view/element`.
Other properties are read-only: `.active` returns a copy of ascending sounding MIDI pitches; `.low`, `.high`, `.system`, `.spelling`, `.density`, `.scheme`, `.firstFret` and `.frets` return the resolved/requested values described above. `.tuning` returns a copy of resolved open-string MIDI pitches. Configure the remaining values through attributes.

The geometry getters `.whiteKeyWidth`, `.blackKeyWidth`, `.whiteKeyHeight`,
`.blackKeyHeight`, `.fretWidth`, `.stringSpacing` and `.stringWidth` return the
positive finite pixel request or `undefined`. Missing, empty, nonnumeric,
non-finite, zero and negative geometry attributes use default geometry;
removing an override restores the responsive/theme default. `.follow` returns
the requested mode. `.scrollable` is a read-only boolean describing effective
keyboard scrolling, `false` by default. `.fitToWidth` is its inverse, `true` by
default. Configure them with attributes; `.scroll()` remains the inherited
HTMLElement method. For both `scroll` and legacy `fit-to-width`, an empty or
`true` attribute enables that setting; `false`, `0`, `no` and `off` disable it,
ignoring case and surrounding whitespace. Other present values enable it.
These keyboard settings do not change staff/fretboard layout or replace the
held-note tracker or player.

`PitchViewElement`, `PitchViewType` and `definePitchViewElement(tag?)` are exported from `@webmusic/score/view/element`. Registration is idempotent and SSR-safe; `defineAllViewElements()` registers all View tags. There are no emitted events or public commands.

**Accessibility.** Each surface is a labeled passive graphic (`role="img"`) with current-pitch labels. It has no playable or focusable piano keys; the keyboard’s visual active state is not a button’s `aria-pressed` state. Configure it with native controls outside the component.

<details class="component-section">
<summary>Styling</summary>

By default, the keyboard fits every key in its range without horizontal
scrolling. `scroll="true"` preserves fixed or minimum key widths and allows
local scrolling; in that mode, `follow="active"` reveals newly sounding pitches
while repeated snapshots and note releases leave manual scrolling in place.
The fretboard preserves readable marker sizes and scrolls locally when its
range does not fit. Wider fretboards expand fret spacing without enlarging
the dots. Staff lines fill the container while noteheads retain their staff-space size. An
overflowing surface is one keyboard focus stop for native scrolling; the musical input is unchanged.


The passive status exposes `pitch-status`, `pitch-status-indicator` and `pitch-status-message` parts and the shared `--wm-status-*` tokens.

The light-DOM component uses the public [pitch presenter tokens](/uikit/views-analysis/pitch/). Its rendered nodes expose `root` plus `board` for keyboard, or `root` plus `svg` for staff/fretboard. The presenter owns resizing and note graphics; the application owns host layout and spacing. There is no internal settings bar or additional sibling view. Motion follows the surrounding `data-motion` setting and reduced-motion preference.

All three types inherit `--wm-component-background`, `--wm-component-border` (complete shorthand) and `--wm-component-radius`, overridden by `--wm-pitch-surface-background`, `--wm-pitch-surface-border` and `--wm-pitch-surface-radius`. The default frame remains transparent and borderless. Set `--wm-surface: transparent` for transparent nested surfaces. `--wm-foreground` and `--wm-accent` control shared ink and highlights; specific note/pitch paint tokens take precedence.

Keyboard keys use `--wm-note-key`, `--wm-note-key-alt`, `--wm-note-border`, `--wm-note-label` and `--wm-note-radius`. Staff lines use `--wm-pitch-staff-line`. Fretboard geometry uses `--wm-pitch-fret-neck`, `--wm-pitch-fret-wire`, `--wm-pitch-fret-nut`, `--wm-pitch-fret-string` and `--wm-pitch-fret-inlay`. Theme changes on the host or an ancestor apply directly to the existing DOM/SVG without replacing the note tracker or held notes. Select exposed parts using ordinary light-DOM selectors such as `score-pitch-view [part~="board"]`.

Key outlines fall back from `--wm-note-border` through `--wm-control-border` and `--wm-border`
to `#d8d8d8` in a light scheme, matching component frames, or `#333` in a dark scheme.
Set `--wm-border` on a shared
ancestor to give a player, score view and keyboard the same border color.

</details>
