`<score-view>` displays a loaded score as `piano-roll` (default), `staff`, `waterfall`, `map` or `thumbnail`. Each instance renders one surface. Select `type` in the demo’s external Parameters; only relevant drawing controls appear, and switching back restores their retained values.

## Import

```html
<script type="module">
  import {defineScorePlayerElement} from '@webmusic/score/play/element';
  import {defineScoreViewElement} from '@webmusic/score/view/element';
  defineScorePlayerElement();
  defineScoreViewElement();
</script>

<score-player id="piece" src="/mxl/Arabesque%20No.1.mxl"></score-player>
<score-view player="#piece" type="staff"></score-view>
```

The demo starts in staff mode with `public/mxl/Arabesque No.1.mxl`, a notation source for Debussy's *Arabesque No. 1* with one piano part and two staves. The player loads the MXL once and the view borrows the parsed score.

The demo contains one player and one score view. Expand the player’s Parameters group to configure playback. Copy includes both tags; Reset restores their initial attributes. The thumbnail type can borrow the player’s loaded score while remaining a static preview.

## Annotations and compact layout

All five passive types show supported directions retained in the Score: words such as
`rit.`, rehearsal labels, dynamics, metronome marks, pedal signs/lines and
crescendo/diminuendo hairpins. The staff places them around notation; the other
types place them along their time axis with compact labels and span lines.
Dense labels may be abbreviated or reduced to markers; SVG titles retain their
full text. The other types do not reproduce staff engraving placement. These
directions are visual and do not change playback tempo, volume or sustain.

Set `show-annotations="false"` to hide these directions in any type. The demo’s
**show-annotations** control applies to every type and is included by Copy and
Reset. `.options.showAnnotations` overrides the attribute. Changing this option
retains the loaded score and playback position.

```html
<score-view player="#piece" type="staff" show-annotations="false"></score-view>
```

Hidden annotations reserve no drawing space. Staff height is recomputed from
the remaining notation, with compact gaps between staves and at the outer
edges. Notes, rests, clefs, key/time signatures, beams, tuplets, ties, slurs and
articulations remain visible. Leave `height` unset to let the component shrink;
an explicit height still defines the application’s viewport.

## Geometry

Time, pitch and instrument dimensions are separate. Changing a note's displayed
length does not change its duration or playback rate.

An editor-bound piano roll instead uses written quarter-note coordinates, with
`.options.pixelsPerQuarter` (default `64`) and `.options.editingGrid` (default
`[1, 4]`); `configure()` accepts both for `piano-roll`. Its pitch lanes default
to `20px`; explicit `note-height`, `min-pitch` and `max-pitch` still apply. Its
default range includes MIDI 48–84 and expands to include the notes; a single
explicit bound limits the computed opposite bound instead of being crossed by it.
`pixels-per-second` and `note-spacing` belong to the
passive renderers below. The editing grid currently draws notes and a quarter
ruler; expressive annotation strips remain on the passive views.

| Surface / dimension | Attribute | Effect |
| --- | --- | --- |
| Piano-roll note length / waterfall note length | `pixels-per-second` | Nominal seconds become horizontal pixels in piano roll and vertical pixels in waterfall. Larger values draw longer notes. |
| Piano-roll note thickness | `note-height` | Height of each MIDI pitch lane in px. |
| Waterfall note width | `white-note-width` / `black-note-width` | Exact natural-note / accidental pitch-column widths in px. |
| Gap between note spans | `note-spacing` | Subtracted from piano-roll / waterfall duration length; `0` keeps the full span. |
| Staff notation size | `note-height` | Scales staff notation; spacing also accounts for glyph clearance. |
| Keyboard key width / length | PitchView `white-key-width`, `black-key-width` / `white-key-height`, `black-key-height` | Independent pixel widths and heights for a separately composed keyboard. |
| Fretboard width / string layout | PitchView `fret-width`, `string-spacing`, `string-width` | Fret spacing, distance between strings and string stroke thickness. |

[`<score-pitch-view>`](/score/element/view/score-pitch-view/) owns the keyboard and fretboard
settings. To align a separate keyboard with waterfall notes, match their pitch
range and column widths and use one shared horizontal scroller, as below.

## Views

### Piano roll

`type="piano-roll"` draws pitch vertically and score time horizontally. It follows the score position and highlights active notes. `pixels-per-second` and the pitch range control the drawing’s geometry. Annotations occupy a compact strip above the notes, aligned to nominal seconds. Hiding them removes the strip and reduces the natural height.

### Staff

`type="staff"` preserves each part’s source staff assignments as separate layers by default (`split-staves="true"`). MusicXML note-to-staff assignments therefore remain visible after import. Set `split-staves="false"` to combine the staves within each part; different parts remain separate. This changes the drawing without reassigning notes in the score or restarting playback.

Staff notation uses the Score's written note values, spelling, rests and voices.
Eighths and shorter values form beam groups, including secondary beams and
hooks; source beam marks take precedence over automatic meter-based grouping.
Tuplets keep their ratios and group numbers, with brackets when needed.
Authored up/down stems, ordinary same-staff slurs, ties, hidden spacing notes
and measure-level clef changes are retained. Stored measure boundaries govern
the drawing, including pickups and later changes of time signature.

All layers align the same written onsets and share a horizontal scroll position
and playhead, so the displayed staves advance together. The bottom timeline
supplies manual horizontal scrolling. `scroll-type` selects page, note or bar
following; `default-key` supplies a key signature when none exists.

A system-start line connects the displayed staves. Staves belonging to the same
part are grouped with a brace and barlines extending across their gaps.
Noteheads, stems, flags and beams follow active-note highlighting; shared
glyphs remain highlighted while any associated note is sounding. These are
drawing features and add no controls.

One full-height divider marks the edge of the fixed signature area. Scrolling notes are clipped outside that area so they do not cover the clefs or signatures.

Bar following keeps the measure start visible when it fits, then follows the current beat if the measure exceeds the viewport. Following also resumes after a hidden container becomes visible. A manual pan remains in place during resize until another player position requests following.

Default spacing gives noteheads, accidentals and other marks room to draw.
A positive `pixels-per-second` requests rhythmic spacing using
`pixels-per-second × 60 / initialQpm` pixels per quarter; glyphs can add width,
so staff notation is not a linear time ruler. Later tempo changes move the
playhead through the complete score time map without changing written values.

The renderer reads stored rational quarter positions directly, preserving
triplets without rounding to a 1/16-quarter grid. MusicXML supplies notation
that MIDI cannot recover, such as authored beams, spelling and clefs. When
written values or clefs are absent, the drawing uses readable duration/clef
inference while preserving the Score's timeline; that is not a reconstruction
of the original sheet music. Active-note highlighting uses nominal sounding
times independently of the written layout.

Part-local clef changes are retained at their exact positions, including inside
a measure; the fixed header follows the clef at the visible position. Authored
clefs are respected even when ledger lines are needed. For scores without a
clef map, inference balances ledger lines against unnecessary changes and
protects ties and tuplet groups.

Source words such as `rit.` and tempo instructions, rehearsal marks, dynamics,
metronome marks, pedal signs/lines and crescendo/diminuendo hairpins are drawn
at their stored musical positions. Placement and supported text styles are
retained, with space reserved around nearby notation. Tuplets respect source
number visibility. Staccato, tenuto, accent, marcato and staccatissimo marks,
source rest positions and barline styles are drawn. Ties and slurs use separate
endpoint and collision rules, including authored slurs between staves of one part.
These visual directions do not introduce playback automation.

Cross-staff and cross-measure beams, nested tuplet layout, complete grace-note
engraving, lyrics and page/system justification remain outside
this scrolling renderer's supported subset.
[`<score-sheet-view>`](/score/element/view/score-sheet-view/) retains the optional OSMD
page-engraving workflow. The staff type needs no separate engine option or
additional installation.

### Waterfall

`type="waterfall"` draws falling notes on piano-style pitch columns, with no
embedded keyboard. By default, occupied octaves fit the container width. Set
`show-only-octaves-used="false"` for the standard A0–C8 piano range, or set
positive `white-note-width` / `black-note-width` values for fixed natural-note
and accidental column widths in pixels. These widths control falling-note
geometry; overflow pans inside the component. Container resizing retains the
score position and active notes.

Without an explicit height, the falling-note viewport uses the score duration
at the selected time scale, bounded to 80–200px. A requested height uses the
available viewport for the notes. The [imperative renderer](/score/api/view/#render-a-waterfall)
retains its explicit pitch-width defaults.

When an application also needs a keyboard, compose a separate
[`<score-pitch-view>`](/score/element/view/score-pitch-view/) around the same player.

#### Align a waterfall and keyboard

This demo uses the opening passage of Arabesque No. 1 and one player.
Both views use MIDI 48–83 (C3–B5), 32px natural columns and 20px accidental
columns. The 21 natural notes make a 672px track. Change **Pitch width**
to resize both views together, **Note length** to change only the waterfall's
time scale, and **Key height** to change only the keyboard. A narrow container
pans their shared track. Press Play to see the held keys follow the notes.

Use the same structure with a score file in your application:

```html
  import {definePitchViewElement, defineScoreViewElement} from '@webmusic/score/view/element';
  defineScorePlayerElement();
  defineScoreViewElement();
  definePitchViewElement();
</script>

<score-player id="falling-piece" src="/midi/Arabesque%20No.1.mid"></score-player>
<div class="shared-pan">
  <div class="pitch-track">
    <score-view type="waterfall" player="#falling-piece"
      min-pitch="48" max-pitch="83" white-note-width="32" black-note-width="20"
      pixels-per-second="64" note-spacing="0" show-annotations="false" height="180"></score-view>
    <score-pitch-view type="keyboard" player="#falling-piece" low="48" high="83"
      white-key-width="32" black-key-width="20" white-key-height="80" black-key-height="50"
      scroll="true" follow="none"></score-pitch-view>
  </div>
</div>

<style>
  .shared-pan { max-width: 100%; overflow-x: auto; }
  .pitch-track { display: grid; grid-template-columns: minmax(0, 1fr); gap: 0; width: 672px; }
  .pitch-track > * {
    width: 100%; min-width: 0; margin: 0;
    --wm-component-padding: 0;
    --wm-component-border: 0;
    --wm-stage-surface-padding: 0;
    --wm-stage-surface-border: 0;
    --wm-pitch-surface-padding: 0;
    --wm-pitch-surface-border: 0;
  }

```

Explicit `min-pitch` / `max-pitch` preserve that exact waterfall range. The
matching `low` / `high` select the same keyboard keys. `scroll="true"` preserves
the keyboard's explicit key widths instead of fitting them to its container.
Zero presenter insets align their left edges; `follow="none"` prevents the keyboard from panning
independently. Disabling annotations removes the waterfall's side rail from
this shared pitch grid. If you resize the columns in application code, update
both views and the track width together.

Annotations follow the vertical time axis in a side rail. Nearby words and
directions share wrapped labels with leaders to their musical positions;
separate span tracks retain pedal and hairpin durations. Hiding annotations
returns the rail's width to the note columns without changing a requested
viewport height.

### Map

`type="map"` gives a whole-piece navigation strip using note-density cells, bar numbers and score landmarks. `for-part` filters the density by part id or name; `cells` bounds the cell count. Long scores group bars rather than creating per-note graphics. Scores without bar structure use an even division and have no bar ruler marks.

Directions occupy a compact strip above the density cells at their quarter
positions. `show-annotations="false"` removes that strip and expression labels;
the bar ruler remains available for navigation.

Click a cell or seek through the lane with its pointer/keyboard controls. The view emits `webscore:seek` with `{quarters, seconds}` in nominal score time and seeks the bound player. It prefers `seekNominal(seconds)`; structural targets with only `seek(seconds)` receive rate-scaled time. A failed player seek is reported and the local position rolls back when no newer state superseded the request. Without a player, navigation updates local inspection and still emits the event.

The projection remains available as [`createScoreMap(score, options)`](/score/api/view/), with no DOM or transport ownership.

### Thumbnail

`type="thumbnail"` makes one static piano-roll layout and scales it into the box.
Its natural height is `3rem` plus one compact annotation strip when directions
exist; normal stage padding stays inside that height. Hiding annotations returns
the component to `3rem`. Nearby directions form overview groups with a readable
representative label and count; SVG titles and accessible descriptions retain
the complete text and musical ranges. Labels keep their readable size when an
explicit height fits the notes into the remaining space.
Very short explicit heights scroll inside the stage so the annotation strip
cannot collapse the note preview to zero height.

Note color defaults to `var(--wm-score-view-note, currentColor)`. `note-color`
accepts CSS colors or an RGB triple; `.options.noteRGB` overrides the attribute,
and `.options.noteColor` overrides both. There is no active-note highlighting,
seeking or playback animation inside the preview. `.active` is empty.
Playback time can still be read through `.currentTime` when a player is attached,
but time changes do not redraw the thumbnail.

```html
<a href="/songs/1">
  <score-view type="thumbnail" src="/midi/Arabesque%20No.1.mid" width="180" height="48"></score-view>
</a>
```

## Data and playback

Without an editor, source precedence is explicit `.score`, then `src`, then the selected player’s resolved score. Explicit URLs load through [`@webmusic/score/io`](/score/api/io/). A player-only view borrows data without another fetch. Changing `type` reuses the resolved score and player snapshot while replacing the old presentation.

The `player` selector must resolve uniquely in the current Document or ShadowRoot. Native snapshots initialize position, including paused state, then data/state/time updates keep it current. Late or replaced targets rebind; invalid or ambiguous selectors remain unbound. Disconnect cancels pending work and releases owned subscriptions and renderers without stopping playback. No type creates a player or audio resource. Only `map` sends seek commands.

Native binding prefers the target's `.playback` [shared source](/score/api/#shared-playback-observation).
An available source suppresses duplicate legacy events. A target without a source,
or one reporting `unavailable`, retains the compatibility snapshot/event path.
`data-player-state` exposes resolution and readiness. An explicit Score with a
different identity from native playback suppresses incompatible highlighting and
map navigation; use the same Score instance to share data intentionally. A custom
target replacing its `.playback` property dispatches `webmusic:sourcechange`.

Missing source data displays a quiet square waiting animation. Loading a URL or borrowing a native player whose source is loading displays the shared square loading animation, including while a replacement source is pending. Native source failures remain visible; independent explicit view data takes precedence. Both retain a screen-reader status message and respect reduced-motion preferences. The three note views show an empty status for a score without notes, and load or drawing failures show an accessible error message. Replacing the source or drawing options retries the applicable work. Disconnect also releases the waterfall resize observer.

## Piano-roll editing

Bind a [Score document](/score/element/edit/score-document/) and add `editable`
to edit its existing piano-roll surface. The document owns content and history;
the View borrows its Core editor port. The second composition demonstrates this
different source relationship while retaining the passive main demo above.

<ScoreEditingDemo />

```html
<script type="module">
  import {defineScoreDocumentElement} from '@webmusic/score/edit/element';
  import {defineScoreViewElement} from '@webmusic/score/view/element';
  defineScoreDocumentElement();
  defineScoreViewElement();
</script>
<score-document id="notes" src="/midi/Arabesque%20No.1.mid"></score-document>
<score-view editor="#notes" type="piano-roll" editable></score-view>
<score-view editor="#notes" type="staff"></score-view>
```

Click selects; Shift-click adds/removes a note. Drag a note to move it in time
and pitch; drag its right edge to resize. Double-click empty space inserts a
quarter note. Alt-drag inserts a note with a previewed duration. Both insertions
start at the editing-grid cell under the pointer, so the new note covers that
point; pointer hits use the displayed note geometry, and double-clicking or
Alt-clicking an existing note selects it instead of inserting another. Moves and
resizes travel in exact editing-grid steps, so an off-grid note keeps its offset;
only insertion uses the absolute grid cell. The focused grid handles arrows,
Shift+Left/Right for duration, Delete/Backspace, Ctrl/Cmd+A, Ctrl/Cmd+Z,
Shift+Ctrl/Cmd+Z and Ctrl/Cmd+Y. Keyboard input in the numeric form or elsewhere
is not intercepted. Escape is consumed only when it cancels a gesture or draft,
so an enclosing dialog still receives it otherwise.

The **Note values and keyboard alternatives** disclosure includes a native
**Select existing note** menu. Open the disclosure with the keyboard, tab to
the menu and choose a note using its native keys. Labels identify the part name
and number, written pitch, quarter onset, voice and note number; notes are ordered
by part, onset and pitch, with stable ordering for ties. Selecting a note updates
the value fields without changing content
or history. **No selection** clears selection; a multi-selection made elsewhere
appears as a summary until you choose one note or clear it. Deletion removes its
option, and undo restores the option without restoring selection.

Numeric fields belong to the selected note at its committed document revision.
A different selection or document revision refreshes them, including external
edits and undo/redo, without moving focus. Playback and focus changes preserve
unsubmitted values for the same target and revision. Shared previews appear on
the grid but do not replace this committed numeric baseline. With no single
selected note, Apply is disabled and the fields remain usable as insertion values.

The labeled onset/duration fields accept integers, decimals or fractions;
other controls provide written MIDI pitch (integer 0–127), velocity (integer
1–127), insertion part and edit/history buttons. An empty or non-integer pitch
or velocity is reported as an error, never treated as zero. Apply changes one
selected note and submits only the fields that differ from its committed
values; an unchanged Apply reports **No change** and adds no history item,
dirty state or redo loss. Insertion uses the chosen part's first voice, or voice `1` for
an empty part. A document needs a part before notes can be inserted. Unsupported
tie/tuplet/grace repairs fail visibly through the same semantic commands.

A drag publishes revision-bound `editpreview` drafts and adds one history item
on successful completion. Escape, cancellation or lost capture of the dragging
pointer, a move after its primary button was released, focus/window blur,
viewport size changes, mode/options changes, detach and a changed document
revision cancel the gesture. A failed latest preview cannot commit an earlier valid preview.
The grid redraws newly visible notes when its containing viewport changes size;
playback updates move the playhead and sounding notes without rebuilding it.
States do not rely on color alone: a selected note has an outer ring, an inner
contrast ring and a visible right-edge resize handle; a draft has a dashed
outline and lighter fill; a sounding note fills its whole pitch lane. A live
status reports selection, drafts and failures and changes only when its text
changes. The empty editor still exposes the grid and numeric insertion controls.
Without `editable`, the grid is a labeled graphic outside the tab order, with no
instructions, selection gestures or form controls.

Each View owns an interaction session by default. Assign the same
`.interactionSession` from the bound editor to share selection and drafts across
surfaces. Foreign-document sessions are rejected. Disconnect disposes only a
View-created session; a supplied session and editor remain caller-owned.
Replacing or clearing this property restores the compatible player's current
position immediately, including while paused. Clearing it creates a new
View-owned session; it does not dispose the previously supplied session.
If a cleanup callback synchronously requests another editor or reconnects the
View, the newer attachment remains active; the old cleanup releases only its
own session, subscriptions and presentation.
Selection is pruned when notes disappear and is not restored by undo.

`.editor` takes precedence over the `editor` selector; assigning `undefined`
restores selector lookup. Selectors require one target in the current root and
track late insertion, removal and `webmusic:sourcechange`. An editor alongside
independent `.score` or `src` is `source-conflict`: object setters reject it
before replacement, and conflicting attributes disable editing until corrected.
No View creates an editor implicitly. Read-only editor binding works for all
types; `editable` is supported for piano roll and staff.

An optional player contributes time only when its applied document ID and
revision exactly match, its binding is ready, and `documentCoordinates` is true.
Pending, failed, foreign or repeat-expanded unmapped playback suppresses
playheads, active notes and map seeking. The editor's newly committed content
stays visible while playback catches up. `editcommit` reports a document commit,
not playback readiness.

## Staff input

Use `type="staff" editable` with the same document owner. The notation surface
retains its own input cursor, duration, octave, accidental, part, voice and
staff; document content and undo history remain shared with the piano roll.
The demo uses an original two-measure MusicXML fixture: four quarter notes in
the first measure and a whole rest in the second. Its separate document keeps
the MIDI example above independent.

<StaffEditingDemo />

```html
<score-document id="notation" src="/musicxml/StaffEditing.musicxml"></score-document>
<score-view type="staff" editor="#notation" editable></score-view>
<score-view type="piano-roll" editor="#notation" editable></score-view>
```

Focus **Staff note input** and press **N** to enable note input, then **A–G**
to enter a spelled pitch. **1–7** choose whole through sixty-fourth note
values; **0** enters a rest. Left/Right moves the cursor by the
current duration, Up/Down changes the octave, and Escape exits note input;
when input is already off, Escape is left to enclosing handlers. Delete or
Backspace replaces the selected event with a rest, with or without note input
enabled. Ctrl/Cmd+Z, Shift+Ctrl/Cmd+Z and Ctrl/Cmd+Y operate the shared document history.
The shortcuts apply only to the focused notation surface, never to text fields.

The labeled fields and buttons supply the same commands without shortcuts:
choose **Insert into part**, **Voice**, **Staff**, **Cursor (quarters)**,
**Duration (quarters)**, **Dots**, **Octave**, **Accidental** and **Pitch letter**,
then **Insert note** or **Insert rest**. Empty **Staff** or **Octave** values
are reported as errors, not read as zero. A command applies only fields whose
values were edited, so an unchanged focused field cannot reset the staff.
Selecting an existing event sets the input position and copies its duration
when it is one whole through sixty-fourth value with up to two dots; durations
such as a piano-roll resize to 5/4 quarters keep the current duration setting.
**Delete selected** replaces the event's span with a rest spelled the same way
and reports an unsupported structure for other durations. A committed entry
advances the cursor. Input changes publish `editcommit` or `editerror`;
staff entry is atomic and has no drag preview. Cursor, part, voice, staff,
duration, octave, accidental and enabled note input persist when attributes,
`.options` or `configure()` re-render the View; a new editor attachment or type
change starts note input disabled.

An entry must fit completely inside one existing authored measure. Entering
within a rest splits it as necessary and fills the selected voice/staff's gaps
with actual written rests. It may replace fully covered notes, but cannot cut
through a sounding note. Enter **Voice** `2` to add an independent voice while
retaining the imported first voice. Every note/rest entry and its rest repair
use one undo item.
Set the cursor to `4` in the demo to enter the second measure, or use Undo in
either surface to restore the previous document.

This first notation-input subset supports simple monophonic measure/voice/staff
lanes. Chords, ties, tuplets, grace notes, authored beams/slurs, hidden or
unpitched events, cross-bar entry and arbitrary voice repair fail explicitly.
Staff editing does not reconstruct measures from MIDI: after importing MIDI in
this demo, the roll remains editable, but staff entry reports the missing
authored-measure requirement. Reload the configured MusicXML source to restore
its notation. Export MIDI retains playback notes and loses written rests,
voices and other notation details; it does not mark this notation document
saved. **Export MusicXML** retains supported staff-entry notation, voices and
rests on the demo's binary quarter grid and marks the exported content identity
saved. The demo requests 960 divisions per quarter, preserving positions down
to 1/64 quarter and double-dotted sixty-fourths exactly. Imported arbitrary
rhythms retain the serializer's fixed-resolution limits. A download request
does not confirm that the browser finished writing a file.

| `note-color` / `active-note-color` | attributes | Score-renderer idle/active colors; the Element’s active default is red `rgb(240, 84, 119)`. `note-color` also styles thumbnail. Map uses timeline tokens. |
| `.score` | writable property | Assign a loaded Score; overrides `src` and player data, cancelling obsolete loads. |
| `.options.pixelsPerQuarter` / `.options.editingGrid` | properties | Editor piano-roll scale (positive pixels/quarter, default 64) and positive rational snap grid (default `[1, 4]`). `configure()` accepts them for `piano-roll`. |
| `data-editor-state` | reflected state | `ready`, `missing`, `invalid`, `ambiguous`, `unavailable` or `source-conflict`. `missing` and `unavailable` (a target not inserted yet, or a declaration still loading, cleared or disposed) are pending: the view shows no stale content and a polite waiting status. `invalid`, `ambiguous` and `source-conflict` show an error status. A `format` change does not rebind an editor-bound view. |
| `data-editable-state` | reflected state | `readonly`, `ready`, `unsupported-type` or `unavailable` for an editor-bound or `editable` View; `editable` without a ready editor is `unavailable`. Absent on a passive View without `editable`. |
| `data-playback-state` | reflected state | Editor playback compatibility: `unbound`, `ready` or `pending`. A local draft does not make the player binding `mismatched`; the player is compared with committed document content. |
| `configure(configuration)` | method | Atomically select `piano-roll`, `staff` or `waterfall` and replace optional mode-specific `.options`. Invalid modes, malformed options and unsupported keys throw `TypeError` before changing the view. Map/thumbnail use `.type`, `.options` and their attributes. |
| `.options` | writable property | `ScoreViewRenderOptions` override note-renderer attributes; map/thumbnail also honor `showAnnotations`, `noteRGB` and `noteColor`; see the [renderer API](/score/api/view/). |
| `.currentTime` | read-only property | Current nominal score position in seconds. |
| `.active` | read-only property | MIDI pitches at the current score position; empty for map and thumbnail. |

Type-specific attributes stay on the element when another type is selected and do not affect that other surface. Missing or invalid numeric values use their corresponding defaults, except on an editor-bound piano roll: there a finite but unusable `note-height`, `min-pitch` or `max-pitch` (nonpositive, outside 0–127 or crossing), or an invalid `.options.pixelsPerQuarter` / `editingGrid`, makes the editing surface unavailable with an error status and `data-editable-state="unavailable"` until corrected.

`ScoreViewElement`, `ScoreViewElementType`, `ScoreViewSeekDetail`, `ScoreViewRenderOptions`, `ScoreViewType`, `parseColorAttr` and `defineScoreViewElement(tag?)` are exported from `@webmusic/score/view/element`. `ScoreViewElementType` includes all five Element types; the lower-level `ScoreViewType` remains `piano-roll | staff | waterfall`. Registration is idempotent and SSR-safe.

`ScoreViewConfiguration` and `ScoreViewOptionsByType` describe the three full
renderer modes and are exported from both `@webmusic/score/view` and
`@webmusic/score/view/element`. `configure()` validates mode/option keys before
committing; it preserves the current source and playback position. Legacy
`.type` and `.options` assignments remain supported for all five Element types.

```ts
import {ScoreViewElement} from '@webmusic/score/view/element';
const configuredView = new ScoreViewElement();
configuredView.configure({type: 'staff', options: {splitStaves: true, showAnnotations: false}});
```

**Events.** Map emits `webscore:seek`: `{quarters, seconds}` in nominal time.
Editing emits `editpreview` with the successful `ScoreDraftResult` (`status:
"preview"`, interaction snapshot), `editcommit` with the committed
`ScoreEditResult` (`status: "committed"`, document snapshot and change), and
`editerror` with `{error}`. No `editcommit` is emitted for cancellation, failure
or a no-op. All four events bubble and are composed. Staff input emits commits
and errors, with no preview event; waterfall, map and thumbnail have no mutation
gestures.

**Accessibility.** The map uses the shared [timeline interaction](/uikit/transport-time/timeline/). The editable grid and staff-input surface are focusable with a named application role, instructions and a live status; labeled controls supply alternatives to surface shortcuts. A read-only grid is one labeled image outside the tab order; its notes are not exposed as separate options. Staff note input has an explicit on/off button. Passive types provide labeled graphics and current-position highlighting where applicable; thumbnail adds no interactive controls.

<details class="component-section">
<summary>Styling</summary>

Staff layers within one part sit closer together when their notation allows it.
The renderer checks the whole score, including offscreen notes, and retains space
for stems, ties and ledger lines without shrinking the notation. Only visible
annotations contribute to clearance; `show-annotations="false"` removes their
space as well as their marks.

The component fits its containing block. Size the host with `width` / `height` or application CSS. Fixed-height note views use a scrollable [UIKit stage](/uikit/layout-feedback/stage/) so a drawing taller than the box remains accessible. Piano-roll/staff/waterfall use their drawing attributes and `.options`; thumbnail stretches its SVG to the requested box.

Idle notes inherit `--wm-foreground` through `--wm-score-view-note`, with neutral `#333` / `#ddd` defaults for light / dark schemes. Active notes use `--wm-score-view-active-note`, then the shared `--wm-accent`, then the existing red default `rgb(240, 84, 119)`. Explicit `note-color` / `active-note-color` attributes or `.options.noteRGB` / `.options.activeNoteRGB` override those defaults; `.options.noteColor` / `.options.activeNoteColor` accept full CSS colors, including variables. The [imperative renderers](/score/api/view/) retain their separate neutral RGB defaults.

Map uses [timeline](/uikit/transport-time/timeline/) tokens such as `--wm-timeline-lane-height`, `--wm-timeline-background`, `--wm-accent` and `--wm-playhead`. [Status](/uikit/layout-feedback/status/) owns the loading, waiting, empty and error appearance. A separately composed PitchView uses its own [pitch tokens](/score/element/view/score-pitch-view/).

The stage/timeline frame accepts `--wm-component-background`, `--wm-component-border` (a complete border shorthand) and `--wm-component-radius`; the presenter's `--wm-stage-surface-*` or `--wm-timeline-surface-*` tokens take precedence. Set `--wm-surface: transparent` as well when clearing nested drawing surfaces. Staff, piano-roll and thumbnail SVGs have transparent drawing backgrounds.

For staff, piano-roll and waterfall, `--wm-score-view-background` overrides the stage viewport background. Otherwise it follows `--wm-stage-background`, `--wm-stage-surface-background`, `--wm-component-background`, then `--wm-surface`, with neutral `#fff` / `#111` defaults for light / dark schemes.

Map density cells use `--wm-score-view-map`, falling back to `--wm-accent`. Their opacity still represents density. Explicit `.options.noteColor`, `.options.noteRGB` and `note-color` override that default, in that order. Thumbnail follows the same explicit precedence with its separate default above.

All five types use live CSS paint expressions: changing a class, ancestor token or inline custom property updates the existing drawing without reloading the score or moving its cursor. These are light-DOM nodes: target `[part~="root"]` / `[part~="surface"]` on the presenter, and `[part~="drawing"]` on full note views and thumbnail, using ordinary selectors rather than shadow-DOM `::part()`.

The editor exposes light-DOM parts `editor`, `editing-instructions`,
`editing-viewport`, `editing-surface`, `editing-status` and `note-properties`.
Its viewport uses `--wm-score-view-background` then `--wm-surface`, and the border
uses `--wm-border`. Note paint follows the existing note/active-note tokens and
explicit color options. Selection's inner ring and the resize handle use the
viewport background (`--wm-score-view-background`, then `--wm-surface`), so they
contrast with any note fill; outer rings, draft dashes and the playhead use the
current text color. Preserve visible focus and these non-color cues when styling the grid.

The staff editor also exposes `staff-input-surface` and `staff-input-controls`
parts around its focusable notation and labeled command disclosure. It reuses
the existing staff drawing, colors and scrolling. Preserve its visible focus,
selected-note outlines and input cursor when styling it.

```css
score-view {
  --wm-component-background: transparent;
  --wm-surface: transparent;
  --wm-component-border: 1px solid #8899aa;
  --wm-component-radius: .5rem;
  --wm-score-view-note: #cdd8ed;
  --wm-score-view-active-note: #ff6688;
}
```
