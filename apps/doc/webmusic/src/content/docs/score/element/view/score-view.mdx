`<score-view>` displays a loaded score as `piano-roll` (default), `staff` or `waterfall`. Each instance renders one surface; drawing attributes for another type are retained, and ignored, until that type is shown.

The view is read-only. It can [follow an editor](#follow-an-editor) and draw its current content, but it never edits notes; use [`<score-grid-view>`](/score/element/view/score-grid-view/) to edit them.

## Import

```html
<script type="module">
  import {defineScorePlayerElement} from '@webmusic/score/play/element';
  import {defineScoreViewElement} from '@webmusic/score/view/element';
  defineScorePlayerElement();
  defineScoreViewElement();
</script>

<score-player id="piece" src="/mxl/Arabesque%20No.1.mxl"></score-player>
<score-view input="#piece" type="staff"></score-view>
```

The demo starts in staff mode with `public/mxl/Arabesque No.1.mxl`, the *Arabesque No. 1* notation source with one piano part and two staves. The player loads the MXL once and the view borrows the parsed score.

The demo contains one player and one score view.

## Ports and composition

`<score-view>` is a **View** companion. It declares no ports and provides no module
context to children. It borrows the `webmusic.score` source and position of one Score playback owner — a
`<score-player>` or a `<score-rack-part>` — and sends no transport commands. It
never registers with or creates a Session.

| Connection | Form | Behavior |
| --- | --- | --- |
| Containment | Nested inside a player or Rack part | Borrows the nearest one; no attribute needed |
| Explicit input | `input="#id"` | One unique element in the same Document or ShadowRoot |
| Explicit module | `.inputModule = module` | Follows that module's `source` port (`webmusic.score`), or the one `port` names; `null` unbinds |
| Module port | `port="source"` with `input` or containment | Follows the named source port on the selected or enclosing module instead of the owner element |
| Explicit data | `.editor`, `.score`, `src` | Takes precedence over borrowed data; `.editor` excludes the other two |

Playback resolves `.inputModule`, then the explicit selector, then containment, then nothing; a `port` attribute moves the selector or containment onto that module's source port. Views and analysis share one follower, so they see the same notes, position and readiness. An
`input` that is missing, invalid or ambiguous stays unbound, reported by
`data-player-state`, and never falls back to the enclosing scope. Inside a
source-free outer player, nest the view in the member that plays or name that
member with `input`.

```html
<score-player src="/mxl/Arabesque%20No.1.mxl">
  <score-view type="staff"></score-view>
</score-player>
```

## Annotations and compact layout

Only the staff type draws supported directions retained in the Score, and only
when `show-annotations="true"` enables them: words such as `rit.`, rehearsal
labels, dynamics, metronome marks, pedal signs/lines and crescendo/diminuendo
hairpins, placed around the notation. Piano roll and waterfall never draw
annotations and reserve no space for them. These
directions are visual and do not change playback tempo, volume or sustain.

`show-annotations` affects only `type="staff"` and defaults to false. Set
`show-annotations="false"` or omit it to keep the staff's directions hidden.
`.options.showAnnotations` overrides the attribute. Changing
this option retains the loaded score and playback position. On the other types
the attribute is retained but has no effect.

```html
<score-view input="#piece" type="staff" show-annotations="true"></score-view>
```

Hidden annotations reserve no drawing space. Staff height is recomputed from
the remaining notation, with compact gaps between staves and at the outer
edges. Notes, rests, clefs, key/time signatures, beams, tuplets, ties, slurs and
articulations remain visible. Leave `height` unset to let the component shrink;
an explicit height still defines the application’s viewport.

## Four directions

Piano roll and waterfall accept `direction="up|down|left|right"`. For piano
roll it is the direction of increasing score time (default `right`). For
waterfall it is note travel toward the current-time landing edge (default
`down`). Low pitches remain at the left for vertical time axes and at the
bottom for horizontal time axes. Labels keep their normal reading direction.
The staff ignores this attribute and retains its usual layout.

Changing direction preserves the score, nominal position and borrowed player.
`.options.direction` takes precedence over the attribute. Give a vertical
pitch axis an explicit height when fitting it into an application layout.
The [aligned composition](#align-a-waterfall-and-keyboard) demonstrates four
travel directions between two independent keyboards sharing one player.

## Geometry

Time, pitch and instrument dimensions are separate. Changing a note's displayed
length does not change its duration or playback rate.

The piano roll's horizontal axis is nominal seconds. For a written-quarter grid
with bar and beat lines, use [`<score-grid-view>`](/score/element/view/score-grid-view/).

| Surface / dimension | Attribute | Effect |
| --- | --- | --- |
| Piano-roll note length / waterfall note length | `pixels-per-second` | Nominal seconds become pixels along the selected time axis. Larger values draw longer notes. |
| Piano-roll note thickness | `note-height` | Breadth of each equal MIDI pitch lane in px, perpendicular to time. |
| Waterfall note width | `white-note-width` / `black-note-width` | Exact natural-note / accidental pitch breadths in px, perpendicular to time. |
| Gap between note spans | `note-spacing` | Subtracted from piano-roll / waterfall duration length; `0` keeps the full span. |
| Staff notation size | `note-height` | Scales staff notation; spacing also accounts for glyph clearance. |
| Keyboard key width / length | PitchView `white-key-width`, `black-key-width` / `white-key-height`, `black-key-height` | Pitch breadth and key depth in px for a separately composed keyboard, independent of its facing direction. |
| Fretboard width / string layout | PitchView `fret-width`, `string-spacing`, `string-width` | Fret spacing, distance between strings and string stroke thickness. |

[`<score-pitch-view>`](/score/element/view/score-pitch-view/) owns the keyboard and fretboard
settings. To align a separate keyboard with waterfall notes, match their pitch
range and pitch breadths and use one shared scroller on the pitch axis, as below.
The piano-roll type uses equal semitone lanes; choose waterfall in any direction
when exact natural/accidental key alignment matters.

## Views

### Piano roll

`type="piano-roll"` draws equal semitone lanes and score time along the selected direction; the default is time to the right and low pitches at the bottom. It follows the score position and highlights active notes. `pixels-per-second` and the pitch range control the drawing’s geometry. It draws notes only; score directions appear on the staff type.

### Staff

`type="staff"` preserves each part’s source staff assignments as separate layers by default (`split-staves="true"`). MusicXML note-to-staff assignments therefore remain visible after import. Set `split-staves="false"` to combine the staves within each part; different parts remain separate. This changes the drawing without reassigning notes in the score or restarting playback.

Staff notation uses the Score's written note values, spelling, rests and voices.
Eighths and shorter values form beam groups, including secondary beams and
hooks; source beam marks take precedence over automatic meter-based grouping.
Tuplets keep their ratios and group numbers, with brackets when needed.
Authored up/down stems, ordinary same-staff slurs, ties, hidden spacing notes
and measure-level clef changes are retained. Stored measure boundaries govern
the drawing, including pickups and later changes of time signature.

All layers align the same written onsets and share a horizontal scroll position
and playhead, so the displayed staves advance together. The bottom timeline
supplies manual horizontal scrolling. `scroll-type` selects page, note or bar
following; `default-key` supplies a key signature when none exists.

A system-start line connects the displayed staves. Staves belonging to the same
part are grouped with a brace and barlines extending across their gaps.
Noteheads, stems, flags and beams follow active-note highlighting; shared
glyphs remain highlighted while any associated note is sounding. These are
drawing features and add no controls.

One full-height divider marks the edge of the fixed signature area. Scrolling notes are clipped outside that area so they do not cover the clefs or signatures.

Bar following keeps the measure start visible when it fits, then follows the current beat if the measure exceeds the viewport. Following also resumes after a hidden container becomes visible. A manual pan remains in place during resize until another player position requests following.

Default spacing gives noteheads, accidentals and other marks room to draw.
A positive `pixels-per-second` requests rhythmic spacing using
`pixels-per-second × 60 / initialQpm` pixels per quarter; glyphs can add width,
so staff notation is not a linear time ruler. Later tempo changes move the
playhead through the complete score time map without changing written values.

The renderer reads stored rational quarter positions directly, preserving
triplets without rounding to a 1/16-quarter grid. MusicXML supplies notation
that MIDI cannot recover, such as authored beams, spelling and clefs. When
written values or clefs are absent, the drawing uses readable duration/clef
inference while preserving the Score's timeline; that is not a reconstruction
of the original sheet music. Active-note highlighting uses nominal sounding
times independently of the written layout.

Part-local clef changes are retained at their exact positions, including inside
a measure; the fixed header follows the clef at the visible position. Authored
clefs are respected even when ledger lines are needed. For scores without a
clef map, inference balances ledger lines against unnecessary changes and
protects ties and tuplet groups.

When annotations are enabled, source words such as `rit.` and tempo instructions, rehearsal marks, dynamics,
metronome marks, pedal signs/lines and crescendo/diminuendo hairpins are drawn
at their stored musical positions. Placement and supported text styles are
retained, with space reserved around nearby notation. Tuplets respect source
number visibility. Staccato, tenuto, accent, marcato and staccatissimo marks,
source rest positions and barline styles are drawn. Ties and slurs use separate
endpoint and collision rules, including authored slurs between staves of one part.
These visual directions do not introduce playback automation.

Cross-staff and cross-measure beams, nested tuplet layout, complete grace-note
engraving and lyrics remain outside this scrolling renderer's supported subset.
[`<score-sheet-view>`](/score/element/view/score-sheet-view/) lays the same
engraving out in justified systems on pages and edits it like a notation
program. Neither needs a separate engine or additional installation.

### Waterfall

`type="waterfall"` draws moving notes on piano-style pitch columns, with no
embedded keyboard. Notes travel down by default; `up`, `left` and `right` choose
the other landing edges. Occupied octaves fit the available pitch axis. Set
`show-only-octaves-used="false"` for the standard A0–C8 piano range, or set
positive `white-note-width` / `black-note-width` values for fixed natural-note
and accidental column widths in pixels. These widths control falling-note
geometry on either axis; overflow pans inside the component. Container resizing retains the
score position and active notes.

For up/down travel without an explicit height, the note viewport uses the score
duration at the selected time scale, bounded to 80–200px. Left/right travel uses
the available width for time; an explicit height defines its pitch viewport. The [imperative renderer](/score/api/view/#render-a-waterfall)
retains its explicit pitch-width defaults.

When an application also needs a keyboard, compose a separate
[`<score-pitch-view>`](/score/element/view/score-pitch-view/) around the same player.

#### Align a waterfall and keyboard

This demo uses the opening passage of Arabesque No. 1 and one player.
Two independent keyboards face the note surface from opposite edges. **Note
travel** switches between a vertical waterfall and a horizontal piano-style
roll. Both use the waterfall renderer's natural/accidental geometry; the
ordinary piano-roll type uses equal semitone lanes instead.

Every view uses MIDI 48–83 (C3–B5), 32px natural pitch breadth and 20px
accidental breadth. The 21 natural notes make a 672px pitch axis. **Pitch width**
resizes that shared axis, **Note length** changes only the time scale, and
**Key depth** changes only the keyboards. A narrow container pans the shared
track. Press Play to see both keyboards follow the same sounding notes.

<WaterfallKeyboardDemo />

Use the same structure with a score file in your application:

```html
<script type="module">
  import {defineScorePlayerElement} from '@webmusic/score/play/element';
  import {definePitchViewElement, defineScoreViewElement} from '@webmusic/score/view/element';
  defineScorePlayerElement();
  defineScoreViewElement();
  definePitchViewElement();
</script>

<score-player id="falling-piece" src="/midi/Arabesque%20No.1.mid"></score-player>
<div class="shared-pan" tabindex="0" role="region" aria-label="Pan notes and keyboards together">
  <div class="pitch-track">
    <score-pitch-view type="keyboard" direction="down" input="#falling-piece" low="48" high="83"
      white-key-width="32" black-key-width="20" white-key-height="80" black-key-height="50"
      scroll="true" follow="none"></score-pitch-view>
    <score-view type="waterfall" direction="down" input="#falling-piece"
      min-pitch="48" max-pitch="83" white-note-width="32" black-note-width="20"
      pixels-per-second="64" note-spacing="0" height="180"></score-view>
    <score-pitch-view type="keyboard" direction="up" input="#falling-piece" low="48" high="83"
      white-key-width="32" black-key-width="20" white-key-height="80" black-key-height="50"
      scroll="true" follow="none"></score-pitch-view>
  </div>
</div>

<style>
  .shared-pan { max-width: 100%; overflow: auto; }
  .pitch-track { display: grid; grid-template-columns: minmax(0, 1fr); gap: 0; width: 672px; }
  .pitch-track > * {
    width: 100%; min-width: 0; margin: 0;
    --wm-component-padding: 0;
    --wm-component-border: 0;
    --wm-stage-surface-padding: 0;
    --wm-stage-surface-border: 0;
    --wm-pitch-surface-padding: 0;
    --wm-pitch-surface-border: 0;
  }
</style>
```

Explicit `min-pitch` / `max-pitch` preserve that exact waterfall range. The
matching `low` / `high` select the same keyboard keys. `scroll="true"` preserves
the keyboard's explicit key widths instead of fitting them to its container.
Zero presenter insets align their left edges; `follow="none"` prevents the keyboard from panning
independently. The waterfall draws no annotation rail, so its note columns
span the shared pitch grid exactly. If you resize the columns in application code, update
both views and the track width together.

For a horizontal composition, set the view's `direction="right"`, give it a
fixed width for time and a 672px height for pitch, and place a
`direction="left"` keyboard at its right edge with the same 672px height.
The existing width attributes still set pitch breadth, while keyboard height
attributes set depth. Use grid columns for the note surface and keyboard,
match the MIDI endpoints, and pan their common container vertically. Swap the
landing edge for `left`; a keyboard above a rising waterfall faces `down`.
The topic demo applies these settings to both edge keyboards without reloading
the score or creating another transport.

## Data and playback

Without an editor, source precedence is explicit `.score`, then `src`, then the input player’s resolved score. Explicit URLs load through [`@webmusic/score/io`](/score/api/io/). A view with only an input borrows data without another fetch. Changing `type` reuses the resolved score and player snapshot while replacing the old presentation.

An `input` selector must resolve uniquely in the current Document or ShadowRoot; without one, the view borrows the enclosing player or Rack part. Native snapshots initialize position, including paused state, then data/state/time updates keep it current. Late or replaced targets and containment scopes rebind; invalid or ambiguous selectors remain unbound and never fall back to containment. Disconnect cancels pending work and releases owned subscriptions and renderers without stopping playback. No type creates a player or audio resource or sends seek commands.

Native binding prefers the target's `.playback` [shared source](/score/api/#shared-playback-observation).
An available source suppresses duplicate legacy events. A target without a source,
or one reporting `unavailable`, retains the compatibility snapshot/event path.
`data-player-state` exposes resolution and readiness. An explicit Score with a
different identity from native playback suppresses incompatible highlighting;
use the same Score instance to share data intentionally. A custom
target replacing its `.playback` property dispatches `webmusic:sourcechange`.

Missing source data displays a quiet square waiting animation. Loading a URL or borrowing a native player whose source is loading displays the shared square loading animation, including while a replacement source is pending. Native source failures remain visible; independent explicit view data takes precedence. Both retain a screen-reader status message and respect reduced-motion preferences. The three note views show an empty status for a score without notes, and load or drawing failures show an accessible error message. Replacing the source or drawing options retries the applicable work. Disconnect also releases the waterfall resize observer.

## Follow an editor

Assign a [ScoreEditor](/score/headless/view/score-editor/) to `.editor` to draw
an editable document read-only. The view shows the editor's committed content,
or the draft of its interaction session while another surface previews an edit,
and redraws after every commit, undo or redo. It offers no editing gestures,
toolbar or keyboard commands. The editor owns content and history; the view
borrows it and never disposes it.

In this composition, a [`<score-grid-view editable>`](/score/element/view/score-grid-view/)
edits Arabesque No. 1 (`public/midi/Arabesque No.1.mid`) and the staff follows
the same editor. The player auditions committed revisions.

<ScoreEditingDemo />

```html
<score-player id="notes-player"></score-player>
<score-grid-view id="notes-grid" input="#notes-player" editable></score-grid-view>
<score-view id="notes-staff" input="#notes-player" type="staff"></score-view>
<script type="module">
  import {defineScorePlayerElement} from '@webmusic/score/play/element';
  import {defineScoreGridViewElement, defineScoreViewElement} from '@webmusic/score/view/element';
  import {loadScoreEditor} from '@webmusic/score/view/headless';
  defineScorePlayerElement();
  defineScoreGridViewElement();
  defineScoreViewElement();
  // Your page owns the editor; dispose it after detaching every borrower.
  const editor = await loadScoreEditor('/midi/Arabesque%20No.1.mid');
  const player = /** @type {import('@webmusic/score/play/element').ScorePlayerElement | null} */ (document.getElementById('notes-player'));
  const grid = /** @type {import('@webmusic/score/view/element').ScoreGridViewElement | null} */ (document.getElementById('notes-grid'));
  const staff = /** @type {import('@webmusic/score/view/element').ScoreViewElement | null} */ (document.getElementById('notes-staff'));
  if (player) player.editor = editor;
  if (grid) grid.editor = editor;
  if (staff) staff.editor = editor;
</script>
```

Each view owns an interaction session by default, so it draws committed
content only. To show another surface's drafts while they are previewed, assign the same session from `editor.createInteractionSession()`
to `.interactionSession` on both. Foreign-document sessions are rejected.
Disconnect disposes only a view-created session; a supplied session and editor
remain caller-owned. Replacing or clearing this property restores the
compatible player's current position immediately, including while paused.

An editor is attached only through the `.editor` property; there is no `editor`
attribute. Assigning `undefined` detaches it without disposing it. When you
replace a document, assign the new editor before disposing the previous one. An
editor alongside independent `.score` or `src` is `source-conflict`: object
setters reject it before replacement, and adding a `src` attribute later shows
an error until corrected. No view creates an editor implicitly. All three types
can follow an editor.

An optional player contributes time only when its applied document ID and
revision exactly match, its binding is ready, and `documentCoordinates` is true.
Pending, failed, foreign or repeat-expanded unmapped playback suppresses
playheads and active notes. The editor's newly committed content stays visible
while playback catches up.

<details class="component-section">
<summary>Styling</summary>

Staff layers within one part sit closer together when their notation allows it.
The renderer checks the whole score, including offscreen notes, and retains space
for stems, ties and ledger lines without shrinking the notation. Only visible
annotations contribute to clearance; `show-annotations="false"` on the staff
removes their space as well as their marks.

The component fits its containing block. Size the host with `width` / `height` or application CSS. Fixed-height note views use a scrollable [UIKit stage](/uikit/layout-feedback/stage/) so a drawing taller than the box remains accessible. Each type uses its drawing attributes and `.options`. The renderers' scroll containers carry `data-webscore-scrollbar="hidden"`: one scoped zero-specificity rule per document or shadow root hides their scrollbars while wheel, trackpad and keyboard scrolling keep working. Because the rule (`scrollbar-width: none` plus the WebKit `::-webkit-scrollbar` equivalent) has zero specificity, application CSS can restore a bar.

Idle notes inherit `--wm-foreground` through `--wm-score-view-note`, with neutral `#333` / `#ddd` defaults for light / dark schemes. Active notes use `--wm-score-view-active-note`, then the shared `--wm-accent`, then the existing red default `rgb(240, 84, 119)`. Explicit `note-color` / `active-note-color` attributes or `.options.noteRGB` / `.options.activeNoteRGB` override those defaults; `.options.noteColor` / `.options.activeNoteColor` accept full CSS colors, including variables. The [imperative renderers](/score/api/view/) retain their separate neutral RGB defaults.

[Status](/uikit/layout-feedback/status/) owns the loading, waiting, empty and error appearance. A separately composed PitchView uses its own [pitch tokens](/score/element/view/score-pitch-view/).

The stage frame accepts `--wm-component-background`, `--wm-component-border` (a complete border shorthand) and `--wm-component-radius`; the presenter's `--wm-stage-surface-*` tokens take precedence. Set `--wm-surface: transparent` as well when clearing nested drawing surfaces. Staff and piano-roll SVGs have transparent drawing backgrounds.

For staff, piano-roll and waterfall, `--wm-score-view-background` overrides the stage viewport background. Otherwise it follows `--wm-stage-background`, `--wm-stage-surface-background`, `--wm-component-background`, then `--wm-surface`, with neutral `#fff` / `#111` defaults for light / dark schemes.

All three types use live CSS paint expressions: changing a class, ancestor token or inline custom property updates the existing drawing without reloading the score or moving its cursor. These are light-DOM nodes: target `[part~="root"]` / `[part~="surface"]` on the presenter, and `[part~="drawing"]` on the note views, using ordinary selectors rather than shadow-DOM `::part()`.

```css
score-view {
  --wm-component-background: transparent;
  --wm-surface: transparent;
  --wm-component-border: 1px solid #8899aa;
  --wm-component-radius: .5rem;
  --wm-score-view-note: #cdd8ed;
  --wm-score-view-active-note: #ff6688;
}
```
