A complete composition has one command authority and several borrowers. This
example loads an opening excerpt from the public Arabesque No. 1 MIDI, renders a matching recording, and gives both to
Bridge. Audio supplies the sound; the muted Score player supplies musical data,
position and note activity. The waveform, piano roll and chord analysis each use
that existing session.

This example renders with `tailSeconds: 0` so its clip ends with the Score. A
render with an effect or release tail makes the clip longer; the Session's
duration then follows the longer participant.

## Try the transitions

1. Click **Load example**, then **Play**. Loading resumes an application-owned
   AudioContext from your click, loads the public MIDI asset and renders the backing track offline. No SoundFont or optional decoder is required.
2. Click **Attach Score views** during playback. The piano roll and analysis
   borrow the already loaded score; they do not fetch a second source. Detach
   them, pause, and attach again to inspect the paused snapshot.
3. Choose **2×**, pause, and seek with the transport slider. The position stays
   on the original score-seconds axis: the midpoint of the excerpt retains the
   same score position at either rate. Resume to hear the changed speed.
4. Enable **Repeat the Session** to loop the whole Session. Native participants
   schedule both sides of the loop boundary from the Session anchor; other
   participants follow with a lead-in, so this is not a claim of a gapless
   boundary for every engine.
5. Click **Replace source** to switch between the first 16 and 24 quarter-note beats
   of Arabesque No. 1. The old Session pauses while a new score and recording
   are prepared. Successful replacement disposes the previous Session and replaces
   its views. A preparation failure retains the previous source, visibly paused.
6. Click **Dispose session**, including while loading. Pending work cannot install
   a new Session after disposal. Load again to create a fresh session.

The chord panel presents score-derived chord analysis. It does not implement the
proposed `score-chord` playback-preview mode. Two equal-looking positions on this
page are UI observations, not measurements of audible timing. The
[createScoreAudioSession reference](/bridge/headless/score-audio-session/) owns the supported
coordination and error semantics.

## Setup in your application

Install the five packages used by this composition:

```bash
npm install @webmusic/score @webmusic/audio @webmusic/bridge @webmusic/kernel @webmusic/ui
```

Use published versions that are available, or this repository's local workspaces.
The implementation below is compiled by the documentation site against its
workspace packages. Browser audio requires a user gesture and Web Audio support;
this example also requires OfflineAudioContext. Unsupported environments and
loading/command failures appear in the status output.

The composition is ordinary application code: `loadScoreFromUrl` loads the score
and the demo selects an opening excerpt without creating new notes,
`renderScoreToClip` produces its audio, `createScoreAudioSession` creates both
engines under one Session, and a UI transport dispatches Session commands. The application closes
its context when the session is disposed. Bridge releases the players it creates;
removing a view releases only that view's borrowed connection and own resources.

## Three integration choices in one session

| Choice         | Used here                                                        | State and ownership                                                    |
| -------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Web Components | `score-view` and `score-chord-analysis`                                 | Borrow a public playback source; no repeated `src` and no new player.  |
| Headless       | `ScorePlayerModule`, `AudioPlayer`, `SessionTransport`           | Own playback behavior and participate in one Session authority.        |
| API + UI       | Offline rendering, peaks, waveform renderer and `mountTransport` | Produce data or display state supplied by the application.             |

A player selector is a browser convenience around the same nonvisual source
protocol. The owner host in this demo exposes a public `playback` value. Its
snapshot and subscription delegate to the native Score player, while its seek
command delegates to the **Session**, so an interactive follower cannot move only
one participant:

```ts
import type { ScorePlaybackSource } from "@webmusic/score";
import type { ScoreAudioSession } from "@webmusic/bridge";

export function sessionPlaybackSource(
  composition: ScoreAudioSession,
): ScorePlaybackSource {
  const playback = composition.scoreModule.player.playback;
  return {
    snapshot: () => playback.snapshot(),
    subscribe: (listener) => playback.subscribe(listener),
    seekNominal: async (position) => {
      const result = await composition.session.dispatch({ type: "seek", position });
      if (result.status !== "committed") throw new Error("Seek superseded.");
    },
  };
}
```

New companions receive their initial data and state through that protocol.
Application drawing uses animation frames to read current positions; it does not
advance musical time. Command completion comes from `dispatch`, not from an
optimistic button label. The last six command results are bounded diagnostics,
not an unbounded event history.

## Independent loop lengths

A Session loop repeats the whole Session timeline. A participant loop repeats
one participant's content while the Session keeps advancing. The following
separate Session has two native Audio buffer loops from the opening of the public Arabesque No. 1 WAV: one second and
one-and-a-half seconds. Both derive timing from the same
AudioContext; each has its own local phase. The `../headless/arabesque-audio`
helper decodes the recording once and keeps only its opening excerpt, so a
disposed session's next start reuses that excerpt instead of downloading and
decoding the complete recording again.

<IndependentLoopsDemo />

Click **Play loops**, then **Pause** and **Seek Session to 4.25 s**. The expected
local positions are **0.25 s** for the one-second loop and **1.25 s** for the
one-and-a-half-second loop. At **2×**, the content positions retain those meanings
while the loops run faster. The progress bars read actual player positions; they
do not schedule the sound.

The implementation configures each `AudioClipPlayer` with its native
`loop: {start, end}` option and registers the same local bounds as
`SessionTransport.register(..., {loop: {startSeconds, endSeconds}})` participant
options. The Session maps joins, seeks and drift checks into each local phase.
The option alone does not turn a player into a native looping engine.

Each player registers with `durationSeconds: Infinity`, so looping members never
end the Session on their own. The demo does not claim
nonlinear tempo warping, time stretching that preserves pitch, or a shared
writable clock instance.

## What this reference establishes

The code makes ownership, command units, late attachment, source replacement and
cleanup inspectable. Automated checks cover the declared contracts and lifecycle
ordering; actual browser, device and audible behavior needs its own recorded
acceptance. The examples are small application compositions, not a project file
format, undo system, or complete music workstation.
